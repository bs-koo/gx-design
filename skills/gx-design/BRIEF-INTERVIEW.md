# 브리프 인터뷰 — 모호함 제거 게이트

목표: 결과를 바꾸는 미확정 의도를 결정 트리로 펼치고, 필요한 frontier가 빌 때까지 질문해 실행 가능한 브리프 하나를 만든다. [HOST-COMPAT.md](HOST-COMPAT.md)의 결정 기록·답변 게이트·승인 재사용이 단일 계약이다. 요청에서 충분히 확정된 작업은 그 근거를 기록하고 재승인 없이 진행한다.

## 절차

### 1. 사실 수집 (질문 금지 영역)

미확정 핵심 의도 때문에 이 인터뷰가 필요할 때만 수행한다. 사용자가 준 대상과 필요한 의존 자료부터 점진적으로 확인한다. 환경에서 확인 가능한 사실은 묻지 않으며, 작은 작업을 이유로 프로젝트 전체를 전수 탐색하지 않는다. 자료 부족이 실제 결정을 막을 때만 탐색 범위를 넓힌다.

- 사용자가 준 자료·대상 파일, 해당 범위의 기존 산출물, 적용되는 CLAUDE.md·AGENTS.md·context/ 기록. 전체 outputs/를 열거하지 않는다.
- 관련 디자인 토큰·브랜드 가이드·DESIGN.md가 실제 제약이면 그 정본의 필요한 절을 읽는다. 강도·정본이 미확정일 때 [DESIGN-TONE-ANCHOR.md](DESIGN-TONE-ANCHOR.md)의 해당 절을 읽고, 변경되지 않은 기존 기준은 재사용한다.
- 사용자가 언급한 서비스·브랜드·경쟁사의 공개 정보 중 인테이크에 필요한 중립적 사실 확인(접근할 수 없으면 미확인 표시). 미해결 전략을 전제한 경쟁 조사 확장·새 방향 탐색은 브리프 확정 뒤 단계 1에서 한다.

### 2. 결정 트리 구축

요청에서 결정 노드를 도출하고 의존 관계를 표시한다. 상류 → 하류 순서:

- **상류**: 매체 유형(BX / 그래픽 / UX·UI / 영상 / 복합), 프로젝트 목표, 타깃 사용자, 핵심 문제. 첫 라운드 상류 질문 우선순위는 목표·타깃·핵심 문제·매체 순이다.
- **중류**: 산출물 범위와 우선순위, 필수 요구사항, 제약 조건(일정·기술·예산·브랜드 규칙), 필요한 디자인 톤 기준([DESIGN-TONE-ANCHOR.md](DESIGN-TONE-ANCHOR.md) §3), 피할 것(아래), 성공 기준
- **하류**: 톤·스타일 방향, 레퍼런스, 매체별 세부 형식

UX/UI가 포함되면 [UI-QUALITY.md](UI-QUALITY.md) §1에 따라 화면별 목적·핵심 과업·성공 기준을 정리한다. 자료로 확인되는 목적은 직접 기록하고, 전략을 바꿀 미해결 결정만 기존 인터뷰에 포함한다.
핵심 여정은 모드와 무관하게 자료에서 확인되면 직접 기록하고, 요청 범위의 검증에 필요하지만 확인되지 않을 때 다른 frontier 결정처럼 질문한다. 확정된 여정은 검수와 실물 제작에서 재사용한다([VISUAL-QUALITY.md](VISUAL-QUALITY.md)). 사용자가 판단을 명시 위임하면 화면 목적에서 도출한 대표 여정을 `[가정]`과 근거·위임 범위로 기록한다.

**"피할 것" 문항 (중류 제약)**: 미확정 금지 조건이 실제 결과를 바꿀 때만 묻는다. 하류 스타일 선택으로 바꾸지 않는다. 선택적 취향은 필수 의도와 구분한다.

- 선택지가 도움이 되면 [VISUAL-CRAFT.md](VISUAL-CRAFT.md) §1에서 매체에 맞는 설명을 고르고 복수 선택·자유 응답을 허용한다. 특정 룩을 자동으로 사용자 금지 조건으로 만들지 않는다.
- 기존 자료의 텍스트 특징·중립적 비교로 설명한다. 브리프 확정 전 새 레이아웃·룩 스케치를 만들지 않는다.
- 사용자가 요청에 "X 말고"·"뻔한 X 싫다"를 이미 썼으면 묻지 않고 그대로 기록한다.
- 첫 라운드는 HOST-COMPAT의 질문 슬롯 산정표(신규 흐름)를 따른다. 상류 의도를 먼저 해소하고 실제 필요한 제약·톤 자료만 묻는다. 이미 정한 금지 조건과 선택적 취향 때문에 필수 작업을 다시 멈추지 않는다.
- 답은 브리프의 `피할 것`에 남기고, 전략·제작·검수가 금지 조건으로 받는다(톤 기준이 있으면 톤 기준이 상위).

하류 질문은 상류가 해소되기 전에는 frontier에 올리지 않는다.
(첫 라운드에 스타일·컬러·무드 3안을 고르게 하는 것이 대표적 오류다 — 포지셔닝이 정해지기 전의 스타일 선택은 근거가 없다.)

### 3. frontier 계산

frontier = 선행 결정이 해소됐고 이번 결과를 바꾸며 사용자 판단이 필요한 미확정 결정. 자료에서 확인 가능한 사실·기존 기준 안의 구현 세부·이미 확정한 값은 제외한다. 아직 열린 결정에 의존하는 질문은 다음 라운드로 미룬다. 필수 결정과 선택적 선호를 구분하고, 결정 ID·범위 버전·의존성을 기존 기록에 남긴다.

### 4. 라운드 실행 — [HOST-COMPAT.md](HOST-COMPAT.md)의 질문·선택

**요청 해석 카드 (첫 라운드 머리말)**: 첫 라운드 질문 전에 사용자의 한 줄 요청과 1절 사실 수집 결과를 아래 슬롯으로 펼쳐 3~5줄로 보여 준다. 채워진 칸은 ✓, 빈 칸은 ?로 표시한다.

```
✓ 무엇: 사내 교육 신청 웹 화면
✓ 누구·목적: 현업 실무자 / 3분 안에 신청 완료
? 피할 것: —
? 기준 자료(DESIGN.md·레퍼런스): 없음 확인 필요
✓ 범위·기기: 신청 흐름 3화면 / 모바일 우선
```

- 카드는 질문이 아니라 머리말이다 — 슬롯([HOST-COMPAT.md](HOST-COMPAT.md#질문-슬롯-산정표)의 질문 슬롯 산정표)에 넣지 않는다.
- 빈 칸(?) 중 결정 트리의 frontier에 있는 것만 이번 라운드에 묻는다. 하류 칸은 상류가 풀릴 때까지 ?로 둔다.
- "요청을 다시 써 달라"고 되돌려보내지 않는다 — 빈 칸은 이 인터뷰가 채운다.

한 라운드는 현재 frontier를 다루되 인지 부담에 맞게 묶는다. 첫 답으로 해소된 질문은 제거한다. 표시 문항 수를 이해도나 질문 총량 제한으로 사용하지 않는다. 필수 응답 대기 중 해당 결정에 의존하는 제작·파일 변경·위임은 중단한다.

- [HOST-COMPAT.md](HOST-COMPAT.md)의 질문·선택을 따른다. 현재 호스트의 문항 상한이 있으면 그 상한에 맞춰 frontier를 분할하고, 각 묶음이 같은 라운드임을 밝힌다.
- 문항은 결정 하나와 답에 따른 결과 차이를 설명한다. 사실 입력은 자유 응답을 쓰고, 선택이 유용할 때만 옵션을 만든다. 근거 있는 추천만 첫 옵션에 "(추천)"과 이유를 붙인다. 추천 거절·모름·다른 의견도 의미대로 처리한다.
- 상호 배타적이지 않은 선택(산출물 범위 등)은 복수 응답이 가능함을 문장으로 밝힌다.
- 시각 비교가 필요하면 인테이크에서는 기존 자료만 설명하고 새 시안을 만들지 않는다. 브리프 확정 뒤 방향 선택에서는 지원되는 시각 미리보기 또는 텍스트 비교를 제공한다.
- 디자인 톤 기준 문항의 "없음" 선택지 설명에는 DESIGN.md를 고를 수 있는 곳(designmd.co, awesome-design-md)을 함께 적는다 — 고르지 않아도 진행된다는 사실도 밝힌다([DESIGN-TONE-ANCHOR.md](DESIGN-TONE-ANCHOR.md) §3).
- 현재 호스트의 구조화 입력 도구가 header를 지원하면 짧게 쓰되 실제 도구 상한을 따른다. 지원하지 않으면 일반 대화 라벨을 사용한다.

### 5. 트리 갱신

답변을 결정 ID·범위 버전과 대조해 답한 결정만 갱신한다. 빈 응답·등록만 성공·부분 응답·취소·늦은 응답의 처리는 HOST-COMPAT의 답변 게이트를 따른다. 해소된 결정이 하류를 열어 새 frontier가 생기면 다음 라운드로 간다.
질문 수 총량 제한은 없다 — 라운드는 frontier가 빌 때까지 반복된다.

### 6. 탈출구 (사용자 전용)

사용자가 "그만, 진행해"(또는 명확히 같은 취지)라고 하면 현재 설명한 범위의 인터뷰를 종료하고 디자인 판단 위임으로 기록한다. "그만"·"멈춰"만 있으면 작업 중단이다.
미해소 결정은 합리적 기본값을 채우되 브리프에 **[가정]** 으로 표기한다.
이 탈출구는 사용자가 발동하는 것이다 — 스킬이 먼저 권유하지 않는다.
브리프를 [가정] 포함으로 저장하고 요약을 보고한 뒤 별도 승인 질문 없이 다음 단계로 간다. 기존 금지·보존 조건은 유지하며 점검→수정·외부 게시·추가 유료 실행 권한으로 확대하지 않는다.

### 7. 종료 게이트

frontier가 비면:

1. 브리프를 아래 양식으로 정리하고 결정 근거·범위 버전을 기록한다.
2. 큰 방향이 열린 신규 작업이거나 새로 정한 중대한 내용의 실행 의도가 불명확하면 전문과 남은 결정을 제시해 승인/수정을 받는다. 요청·기존 답변으로 필수 의도와 실행이 이미 확정됐으면 `[요청에서 확정]` 또는 기존 승인 근거를 기록하고 같은 승인을 다시 묻지 않는다.
3. 확정 브리프를 `outputs/brief/YYYY-MM-DD_<project>_brief.md`로 저장하고 필요한 단계로 간다. 필수 응답이 남았으면 의존 단계는 대기한다.

## 브리프 양식

- 프로젝트명
- 프로젝트 유형
- 배경
- 목표
- 타깃 사용자
- 핵심 문제
- 필요한 결과물 (우선순위 포함)
- 화면별 목적·핵심 과업·성공 기준 (UX/UI일 때 — UI-QUALITY.md §1)
- 핵심 여정(검증 시나리오) (UX/UI일 때 — 예: 메인 → 상세 → 장바구니, 대상 기기)
- 필수 요구사항
- 제약 조건
- 참고자료
- 디자인 톤 기준 (있을 때: 강도[hard/soft]·팔레트·타이포·톤 요약·원본 파일 경로 — DESIGN-TONE-ANCHOR.md)
- 피할 것 (사용자가 배제한 룩·표현 — 없으면 "지정 없음")
- 성공 기준
- [가정] 목록 (명시 위임 시, 근거·적용 범위 포함)
- 결정 기록 (`id / value / status / source / scope-version / dependencies` — 기존 기록 안에 유지)

## 핵심 모드 조항

- 모드 명시는 존중하고, 없으면 핵심 모드로 시작한다. 실제 범위·복잡도 신호가 있을 때 해당 단계만 승격하며 모드 선택을 첫 질문으로 만들지 않는다.
- 인터뷰 절차는 모드와 무관하게 동일하다 — 결과를 바꾸는 미확정 필수 결정은 frontier가 빌 때까지 묻는다. 핵심 여정도 요청 범위의 검증에 필요하고 자료에서 확인되지 않을 때 묻는다.
- 핵심 모드는 [RUN-BUDGET.md](RUN-BUDGET.md)의 내부 작업량을 줄인다. 모드를 이유로 필수 의도를 생략하거나 [가정]으로 채우지 않는다. 선택적 선호의 `지정 없음`은 가정·위임·사용자 승인이 아니다.
- 종료 게이트와 승인 재사용은 양 모드 공통이며, 방향이 정해진 작업에 전략 3안을 추가하지 않는다.
