# VISUAL-QUALITY — 코드 렌더링 시각 품질 루프

문서 검수만으로는 실물 품질을 보증할 수 없다 — 렌더 이미지를 직접 비평하고, UI 코드는 정상 과업과 관련 예외도 실행해 확인한다.
적용 대상: PRODUCTION-HANDOFF 경로 A(코드 렌더링)와 UI 프로토타입 등 이미지·화면 실물이 나오는 모든 제작. 모드(전체/핵심)와 무관하게 의무다. 영상·모션 그래픽은 아래 `영상 분기`를 따른다.

**읽기 지도**

| 산출물 유형 | 읽을 절 | 건너뛸 절 |
|---|---|---|
| UI·웹 코드 렌더 제작 | 머리 용어·심각도 표, 절차, UI·웹 실행 검증 로그(반응형 폭 선택·여정 시나리오 포함), detect 선택 게이트, 검수 연계, Red Flags | 영상 분기 |
| 정적 그래픽·BX 코드 렌더(배너·키 비주얼 등) | 머리, 절차(4 제외), UI·웹 실행 검증 로그의 `검증 불가: 비실행 산출물` 문단, detect 선택 게이트(HTML/CSS일 때), 검수 연계, Red Flags | 반응형 폭 선택·여정 시나리오·Playwright 미가용 안내, 영상 분기 |
| 영상·모션 그래픽 렌더 | 머리, 절차(4 제외), 영상 분기, 검수 연계, Red Flags | UI·웹 실행 검증 로그, detect 선택 게이트 |
| 생성형 프롬프트 패키지만(실물 렌더 없음) | — (실물이 생기면 해당 매체 행을 따른다) | 전체 |
| gx-redesign 진단(audit) | 머리, 절차 2·3, UI·웹 실행 검증 로그 전체, detect 선택 게이트, 영상 분기(영상일 때) | 절차 5~7(polish는 제작 단계) |
| 검수 축 B | 전체 | — |

검수·진단 역할은 '건너뛸 절'을 적용하지 않는다 — 자기 축이 판정하는 절 전체를 읽는다. 렌더 품질 로그·실행 검증 로그를 판정하는 검수 축 B는 이 문서 전체를 읽는다. `출처` 절은 모든 유형에서 건너뛴다.

**용어**: 진단은 **audit**(읽기 전용 — 지적만 하고 고치지 않는다), 절차 5의 수정 회차는 **polish 패스**(지적 항목을 고친다)라 부른다. 외부 도구의 심각도는 gx 체계로 옮겨 적는다:

| 외부 표기 | gx 심각도 | 기준 |
|---|---|---|
| P0 | Critical | 핵심 과업 차단 |
| P1 | Critical 또는 Major | 접근성 실패 — 과업을 막으면 Critical |
| P2 | Major | 과업은 되지만 품질·일관성을 눈에 띄게 해침 |
| P3 | Minor | 다듬기 수준 |

## 절차

1. **제작 전**: frontend-design 스킬이 가용하면 로드하고, [VISUAL-CRAFT.md](VISUAL-CRAFT.md)의 크래프트 규칙(안티-슬롭·톤 다이얼·일관성·모션)을 제작·비평 기준으로 삼는다.
2. **대표 컷 렌더·캡처**: 전체 렌더 전에 대표 컷(스틸·대표 화면) 2~3장을 먼저 렌더한다. 화면 산출물은 Playwright MCP가 가용하면 뷰포트별로 캡처하고 레퍼런스가 있으면 비교한다 — 없으면 렌더 PNG를 그대로 연다(폴백).
3. **시각 비평(핵심)**: 렌더 이미지를 파일·이미지 보기 도구로 직접 열어 보고 아래 기준으로 비평한다. 명세 값 대조가 아니라 디자인 비평이다.
   - **시각 위계**: 시선이 의도한 순서로 흐르는가
   - **간격·정렬**: 리듬이 일관적인가, 어색한 붙음·벌어짐은 없는가
   - **밀도**: 빈약해 허전하거나 과밀하지 않은가
   - **색**: 균형·대비가 충분한가, 팔레트를 벗어난 색은 없는가
   - **정체성 오독**: 다른 것으로 읽히지 않는가 — "이 심볼이 막대 차트로 보이지는 않는가", "이 키 비주얼이 미완성 와이어프레임으로 보이지는 않는가"를 명시적으로 자문한다
   - **QA 4항목**: AI 아티팩트·렌더 결함(폰트 폴백 흔적, 깨짐) / 기술 정확성(치수·해상도·hex) / 구성 문제(잘림·오버랩) / 스타일 일관성(다른 자산과)
   - **크래프트([VISUAL-CRAFT.md](VISUAL-CRAFT.md))**: 안티-슬롭(§1 4대 기본 룩을 무심코 답습하지 않았는가) / 일관성 잠금(§3 accent·radius·테마가 각 하나인가) / 모션(있으면 [MOTION.md](MOTION.md) §A — 빈도 대비 과한 모션·ease-in·300ms 초과·`transition: all`·reduced-motion 처리) / 시그니처(§5 대담함이 한 곳에 모였는가) / 요소·카피 텔([ANTI-TELL-CHECKLIST.md](ANTI-TELL-CHECKLIST.md) — side-tab 보더·그래디언트 텍스트·가짜 생동감·콘텐츠 텔)
   - **기계 바닥**: 대비 WCAG AA(본문 4.5:1·큰 텍스트 3:1) / 본문 크기 최소 14px(권장 16) / 본문 line-height 1.4 이상 / 줄 길이 과장(영문 ~80자·한글 ~40자 초과 경계) / 헤딩 레벨 건너뜀 / 색 배경 위 회색 본문 / 오버플로·요소 가림. 코드 렌더면 아래 detect 선택 게이트 출력을 이 항목들의 기계 근거로 쓴다.
4. **UI 실행 확인**: UI 코드 산출물은 아래 `UI·웹 실행 검증 로그` 절의 검증과 관련 예외 확인을 수행한다. 비실행 산출물·실행 도구 부재는 같은 절의 제한 기록을 따른다.
5. **polish 패스(수정 → 재렌더 → 재비평)**: 루프는 **최소 1회, 최대 3회**. 회차마다 비평 요지(발견 → 수정)를 제작 문서의 "렌더 품질 로그" 절에 기록하고 변경된 과업의 실행 결과도 갱신한다.
6. **통과**: 자체 비평 Critical 0건이면 전체 렌더로 진행한다. 미검증 항목이 있으면 검증 범위와 남은 수용 체크를 함께 보고하며 기능 통과로 표시하지 않는다.
7. **3회 초과**: Critical이 남으면 자동 진행하지 않는다 — 사용자에게 한계와 대안(경로 변경·수동 보정·명세 조정)을 보고한다.

## UI·웹 실행 검증 로그

실행 가능한 UI·웹 코드 산출물은 위 품질 루프 안에서 아래 항목을 확인하고 제작 문서의 `실행 검증 로그`에 기록한다. 별도 반복 루프를 만들지 않는다. 네이티브·데스크톱 UI는 실제 제공할 기기·입력 방식의 동등한 검증을 적용한다.

- 데스크톱 대표 뷰포트와 모바일 대표 뷰포트에서 레이아웃·오버플로·콘텐츠 가림을 확인한다. 추가 폭은 아래 `반응형 폭 선택`의 위험 신호로 정한다. 요청 범위에 없는 기기 유형은 제외 사유를 기록한다.
- 주요 버튼의 정상 과업·관련 오류·복구 결과와 내부·외부 링크의 실제 대상·실패 여부를 확인한다. 관련 예외는 [UI-QUALITY.md](UI-QUALITY.md) §4에 따라 선택한다.
- 키보드 Tab 이동 순서, 보이는 포커스, 필요한 포커스 이동·복귀와 입력 오류 안내를 확인한다.
- 실제 표시되는 텍스트·제어 요소의 WCAG AA 대비와 지원 테마의 상태별 표시를 확인한다.
- 모션이 있으면 `prefers-reduced-motion` 또는 플랫폼의 동등한 설정에서 상태 피드백을 유지하는 축소·대체 동작을 확인한다.
- 브라우저 콘솔 오류·경고를 수집해 기록한다.

로그에는 `실행 환경 → 확인 항목·재현 조건 → 결과·근거 → 미검증/제외 사유`를 적는다. 같은 문서 안의 절로 저장해도 되며, 검수에는 문서 경로와 해당 절을 전달한다. 스크린샷이나 정적 detect만으로 조작·전체 접근성·성능 통과를 선언하지 않는다.

정적 이미지·영상·비실행 명세는 `검증 불가: 비실행 산출물`과 제외 항목을 기록한다. UI 코드가 있어도 실행 도구·환경이 없으면 `미검증: 실행 환경·도구 제한`, 시도한 방법과 미확인 항목을 기록한다. 미검증 항목은 기능 결함과 구분하고, 기능 통과나 전체 수용 체크 충족을 선언하지 않는다. 필요한 수용 체크를 검증하지 못했으면 검증 범위를 제한해 보고한다.

### 반응형 폭 선택 (위험 기반)

기본은 2폭이다 — 모바일 375×812, 데스크톱 대표 폭(브리프 기기 기준, 없으면 1440×900). 아래 위험 신호가 산출물에 있을 때만 해당 조건을 추가한다. 모든 폭을 기계적으로 늘리지 않는다.

| 위험 신호 | 추가 조건 | 확인할 것 |
|---|---|---|
| 긴 한글·혼합 언어 라벨, 고정 헤더·하단 바·플로팅 버튼 | 320px 폭 | 줄바꿈·잘림, 버튼 확장, 고정 영역이 콘텐츠·입력을 가리는지 |
| 영상·지도·캔버스·넓은 표 | 가로 방향(예: 812×375) | 비율 유지, 조작 요소 접근, 세로 공간 부족 시 핵심 정보 노출 |
| 폼·데이터 표·긴 본문 | 확대 200% | 내용·기능 손실, 두 방향 스크롤, 레이블·오류 문구 잘림([UI-QUALITY.md](UI-QUALITY.md) §4 접근성 실행 체크와 같은 회차) |
| 브리프가 태블릿 등 다른 기기를 명시 | 해당 기기 대표 폭 | 기본 2폭과 같은 항목 |

로그에는 선택한 폭과 그 위험 신호를 적고, 신호가 없으면 `추가 폭: 위험 신호 없음`이라고 적는다.

### 여정 시나리오

브리프·개선 브리프에 `핵심 여정`(예: 메인 → 상세 → 장바구니)이 있으면, 모바일(375×812)과 데스크톱 대표 폭에서 그 경로를 실제 클릭으로 끝까지 따라간다. 핵심 여정이 없으면 화면별 핵심 과업으로 갈음하고 그 사실을 로그에 적는다.

- Playwright MCP가 가용하면 조작은 접근성 스냅샷(snapshot)을 기준으로 하고, 스크린샷은 시각 확인용으로만 쓴다 — 스크린샷 좌표로 클릭하지 않는다.
- 단계마다 도달 화면·실패 지점·콘솔 오류를 실행 검증 로그에 남긴다.

여정 결과는 실행 검증 로그 안에 아래 표로 적는다. 폭이 다르면 행을 나눈다(예: J-01-375, J-01-1440). 검수 회귀 확인과 리디자인 재측정은 같은 경로 ID로 다시 실행한다.

| 경로 ID | 시작 상태 | 단계 | 기대 결과 | 실제 결과 | 실패 조건 | 증거 |
|---|---|---|---|---|---|---|
| J-01-375 | 비로그인, 장바구니 비어 있음 | 메인 → 상세 → 옵션 선택 → 장바구니 담기 → 장바구니(4단계) | 장바구니에 선택 옵션 1건 | 3단계에서 옵션 시트가 하단 바에 가려 진행 불가 | 담기 버튼에 도달하지 못함 | 스냅샷·캡처 경로, 콘솔 오류 0건 |

- `단계`는 조작 단위로 적고 단계 수를 괄호에 쓴다 — [UI-QUALITY.md](UI-QUALITY.md) §1 IA·과업 흐름 점검표의 단계 수 근거다.
- `실패 조건`은 실행 전에 정한다(무엇이 일어나면 실패로 볼지). 실행하지 못한 경로는 `실제 결과`에 `미검증`과 사유를 적는다.

### Playwright 미가용 안내

UI 코드 산출물인데 브라우저 자동화 도구가 없으면 렌더 PNG 열기·수동 확인으로 폴백하되, 설치 방법을 **세션당 1회** 안내한다. 자동 설치하지 않는다.

- Claude Code: `claude mcp add playwright npx @playwright/mcp@latest`
- Codex CLI: `codex mcp add playwright -- npx @playwright/mcp@latest`를 실행한 뒤 Codex를 재시작한다. Windows에서 `npx`가 해석되지 않으면 `npx.cmd`를 사용한다.

## detect 선택 게이트 (선택 — 코드 렌더 산출물만)

impeccable(Apache 2.0)의 탐지 CLI를 **가용할 때만** 기계 검사로 빌려 쓴다. Playwright MCP와 같은 "가용 시 사용·미가용 시 폴백" 패턴이며, 스킬·훅 설치가 아니다(impeccable의 .claude 설치·훅은 도입하지 않는다).

- **실행 조건**: 산출물이 HTML/CSS 코드 렌더이고 Node.js 22.12+·npx가 가용할 때. 미가용이면 [ANTI-TELL-CHECKLIST.md](ANTI-TELL-CHECKLIST.md) 수동 점검으로 갈음한다.
- **실행**: `npx --yes impeccable@latest detect <렌더 폴더 또는 로컬 URL>` 1회. 지적을 표로 옮길 때는 `--json`을 붙인다. 종료코드: 0 = 발견 없음, 2 = 발견 있음, 1 = 스캔 실패(검증 제약으로 기록). 실행 완료·지적 0건은 기계 점검 결과만 나타내며, 동작·접근성·전체 디자인 품질의 통과를 뜻하지 않는다.
- **해석**: 지적은 실제 코드·화면에서 확인하고 사용자 영향에 따라 Critical/Major/Minor로 판정한다. 콘텐츠 비가시·핵심 과업 차단이 확인되면 Critical로 처리하고, advisory는 참고한다. CLI 실행 오류·미지원은 검증 제약으로 기록한 뒤 수동 점검으로 갈음한다.
- **기계 출력은 입력이지 판정자가 아니다**: 브리프·디자인 톤 기준이 의도한 선택(예: 요청된 크림 팔레트)을 지적하면 브리프 우선으로 기각하고, 기각 사유를 렌더 품질 로그에 남긴다.
- **톤 기준 시너지**: DESIGN.md 톤 기준이 프로젝트에 있으면 detect의 design-system 계열 규칙이 폰트·색·radius·타입 스케일 이탈을 기계 검사한다 — 검수 축 A의 보조 입력.

## 영상 분기 (영상·모션 그래픽)

영상은 스틸 2~3장으로 품질을 판단할 수 없다. 대표 컷 대신 아래 두 가지를 만들어 직접 열어 비평한다.

1. **컨택트 시트**: 씬마다 시작·중간·끝 프레임을 한 장에 격자로 모은 이미지.
2. **핵심 구간 프리뷰**: 훅(첫 1~3초)과 시그니처 모션 구간의 저해상도 렌더.

비평 항목은 [MOTION.md](MOTION.md) §B 기준이다: B1 씬 합 = 러닝타임 프레임 검산 / B2 텍스트 가독 홀드 / B4 전환 종류·역할 일관 / B5 첫 1~3초 훅 / B6 게시 플랫폼 안전영역 / 루프 지점(루프 영상이면 끊김 없음). 모션 지적은 MOTION §C 표로 렌더 품질 로그에 남긴다. 위 절차 3의 시각 비평(위계·색·QA 4항목)은 컨택트 시트에 그대로 적용한다.

## 검수 연계

- 검수(REVIEW-AXES) 축 B의 입력에 실물 이미지 경로, 렌더 품질 로그, UI 코드 산출물의 실행 검증 로그를 포함한다.
- 루프 기록이 없는 실물은 검수에서 Critical("품질 루프 미수행")로 처리한다.
- detect 게이트를 실행했으면 출력 전문(또는 "기계 점검 완료·지적 0건")과 실행 제약을 렌더 품질 로그에 첨부한다.

## Red Flags

- 렌더 파일을 저장만 하고 열어 보지 않았다
- "명세 값과 일치한다"만 확인하고 통과시켰다 — 값이 맞아도 조잡할 수 있다. 비평 기준은 절차 3의 항목 전부다
- 렌더 품질 로그 없이 outputs/final/에 실물을 저장했다
