# 2축 독립 검수

목표: 전략 일치와 완성도를 서로 독립된 눈으로 검수한다.
두 축의 결과는 합치지 않는다 — 한 축의 호평이 다른 축의 결함을 가리지 못하게 한다.

## 검수 계약과 ID 계약

검수 보고 머리에는 실행 방식을 명시한다. 제작과 다른 실행 맥락이 실제로 축 B를 수행했으면 `독립 검수(별도 맥락)`, 그렇지 않으면 `재열람 기반 자체 검수(동일 맥락 검수)`라고 쓴다. 독립 맥락에는 짧은 브리프·필수 기준·제품 토큰·실물·기준 예제와 해당 축 규칙만 전달하고, 제작자의 자기평가·'발견→수정' 자기 정당화는 첫 판단 입력에서 제외한다. 원시 로그 경로는 재현·대조용으로 제공한다. 호스트별 위임 가능 여부와 전달 방식은 [HOST-COMPAT.md](HOST-COMPAT.md)를 따른다.

## 최종 산출물 검수 기록

모든 판정은 `산출물 경로 | 버전 또는 해시 | 범위 버전·선택 D/G/CH ID | 필수 수용 조건 | fixture·초기화 | 상태(S-)·여정(J-) | 뷰포트·입력 방식 | 실행 환경·도구 | 관찰 근거 경로 | A/B/C 판정`에 연결한다. 해시를 얻지 못하면 식별 가능한 버전을 사용하고 그 한계를 적는다. 같은 빌드의 다른 상태·폭·fixture까지 검수 완료로 확대하지 않는다.

리뷰어에게 URL/파일, 실행 방법, 필요한 인증 상태, 시작 화면, fixture 초기화 방법과 현재 가용 도구 능력(파일 열람·캡처·조작·영상/오디오 재생)을 전달한다. **먼저 실물에서 관찰한 사실·실패를 기록하고, 그다음 원시 실행 로그·기계 측정과 대조한다.** 제작자 자기평가를 검수 근거로 대신 쓰지 않는다. 필수 증거에 접근할 수 없으면 시도한 방법·도구 실패·미검증 범위를 적고 실제 제품 결함과 구별한다.

제품 결함 심각도(Critical/Major/Minor)와 절차·증거 누락(필수 로그 부재·도구 실패·관찰 미수행)은 별도 필드로 기록한다. 증거가 없다는 이유만으로 실제 제품이 Critical 결함이라고 추정하지 않는다. 절차·증거 누락으로 필수 수용 조건이 미검증이면 해당 범위 PASS를 보류한다.

### 범위별 판정

- `통과(PASS)`: **범위 내 필수 Critical·Major**가 해결되고 필수 수용 조건의 최종 버전 증거가 있다. 전역 Major 0건을 요구하지 않는다. 범위 밖 문제는 기록하며, 수정이 새로 만든 회귀는 관련 범위로 포함한다.
- `수정 필요`: 범위 내 필수 Critical·Major가 남는다. 취향 차이나 관찰하지 못한 가설만으로 결함을 만들지 않는다.
- `미검증`: 필수 수용 조건이 미검증이면 해당 범위 PASS를 보류한다. 범위 밖 미검증은 한계로 보고하고 검증된 범위의 판정과 분리한다.
- `예외 수용`: 사용자가 특정 결함·미달을 명시적으로 수용한 상태다. 결함 ID·조건·수용 근거를 남기며 **해결된 통과**로 바꾸지 않는다.
- 정성 기준이 사용자 취향 판단을 기다리면 기술 검수 상태와 `사용자 확인 필요`를 나눠 보고한다. 문서·프롬프트 패키지의 완성 판정은 생성 이미지·실행 UI·MP4의 품질 통과를 뜻하지 않는다.

### 영향 기반 재검수

수정·재생성·내보내기로 결과가 바뀌면 영향받는 판정을 무효화하고 **최종 파일**에서 다시 확인한다. 변경 ID마다 영향받는 기준·A/B/C 축·상태·폭·여정을 기록하고, 영향 없는 기존 근거는 버전 간 유효 사유를 남겨 재사용한다.

축 B 수정이 브랜드·모바일·여정에 영향을 주면 **A/C**와 관련 회귀도 확인한다. 예: 색·토큰 변경은 브랜드/대비/관련 상태, 컴포넌트 크기 변경은 관련 모바일 폭·키보드·J- 경로, 영상 재내보내기는 최종 프레임·가독 구간·해당 오디오를 재확인한다. 모든 축을 매번 전부 실행하거나 수정한 축 하나만 고정해서 보지 않는다. 새 근거도 같은 기록 필드에 연결한다. [RUN-BUDGET.md](RUN-BUDGET.md)의 단일 총예산을 따른다.

| 접두 | 의미 | 생성 단계·주체 | 재사용처 |
|---|---|---|---|
| D- | 진단 항목 | gx-redesign 단계 1 | 전략·변경 기록·축 C |
| G- | 성공 기준 | 개선 브리프 | 축 C 재측정 |
| S- | UI 상태 | [UI-QUALITY.md](UI-QUALITY.md) §3 | 상태 메시지·검수 |
| J- | 여정 경로 | [VISUAL-QUALITY.md](VISUAL-QUALITY.md) | 진단·실행 검증·회귀 |
| CH- | 변경 항목 | 제작 기록 | 진단/목표 추적·축 C |

## 절차

1. 단순 audit·polish는 오케스트레이터가 관련 A/B/C 판정을 나눠 기록하며 자동 축별 병렬 위임을 하지 않는다. 전체 작업의 축 분리도 필요한 범위만 수행한다. 작업 위험·규모가 별도 검토를 정당화하고 위임 권한·도구가 있으면 **최종 축 B**를 제작과 다른 맥락 1개에 맡긴다. 제작 중 매 단계 새 검수자를 만들지 않는다. 별도 맥락이 없으면 주 에이전트가 [creative-review 스킬](../creative-review/SKILL.md)의 적용 절을 읽고 A/B/C 근거를 별도로 기록하며 자체 검수임을 명시한다. 다른 축의 호평으로 결함을 가리지 않는다.
   - **축 A — 전략 일치**: 입력 = 브리프 + 선택된 전략 + 산출물(+ 디자인 톤 기준이 있으면 그 원본 파일, 레퍼런스 입력을 쓴 제작이면 [REFERENCE-DRIVEN.md](REFERENCE-DRIVEN.md) 경로). 검수 범위 = 목표 적합성, 전략 일치성, **디자인 톤 기준 준수**(있을 때 — [DESIGN-TONE-ANCHOR.md](DESIGN-TONE-ANCHOR.md) §4: hard는 근거 없는 이탈이 결함, soft는 이탈의 근거 기록 여부), **레퍼런스 연계**(레퍼런스를 쓴 경우 — REFERENCE-DRIVEN §6: 근접도 다이얼 일치·저작권 가드 위반 0건).
   - **축 B — 완성도**: 첫 관찰 입력 = 산출물 + 실물 이미지·렌더 결과 경로(존재 시 필수) + 매체 정보·필수 기준·재현 정보 + [ANTI-TELL-CHECKLIST.md](ANTI-TELL-CHECKLIST.md) 해당 절(시각 구조·AI 티가 검수 범위인 UI·그래픽·코드 렌더·Gemini 웹 생성일 때만) + [MOTION.md](MOTION.md) 해당 절(모션이 검수 범위이거나 변경 영향에 포함될 때만 — UI는 §A, 영상은 §B). 직접 관찰 기록 후 관련 렌더 품질 로그·실행 검증 로그의 **원시 근거**를 대조하며 제작자 비평·수정 정당화와 분리한다. 정보 구조·시각·UX/UI·영상·제작 가능성 중 현재 요청·필수 기준·회귀 영향에 해당하는 항목만 판정한다.
2. 각 축은 creative-review의 검수 결과 형식(총평 ~ 최종 승인 여부)으로 보고하게 한다. 단순 작업은 필수 이슈·변경·증거·판정 필드를 보존한 한 개의 간결한 로그로 축을 구분하고 별도 템플릿 문서들을 생성하지 않는다. 관찰·캡처·관련 과업 확인은 일괄 수행하고 적용 규칙은 세션 내 캐시를 재사용한다.
   정보 위계·과업·묶음·읽힘이 현재 검수 범위나 변경 영향에 포함될 때 [DESIGN-JUDGMENT.md](DESIGN-JUDGMENT.md)의 해당 절을 입력에 포함한다. 리디자인은 기존 진단·변경 ID와 변경 전후 증거를 대조한다. 모션만 점검하는 요청은 무관한 위계·AI 티 규칙을 새로 읽거나 감사 범위를 확대하지 않는다. 관련 회귀·필수 수용 조건은 확인하고 기존 증거·ID 계약과 검증 한계 표기를 유지한다.
   UX/UI일 때 두 축에 해당 화면 목적·핵심 과업을 전달한다. 축 A는 적용되는 목적·전략을 판단하고, 축 B는 [UI-QUALITY.md](UI-QUALITY.md)의 **§2 증거 계약**과 현재 요청·변경 영향에 해당하는 §3~4만 적용한다. 시각·UX 비평과 구현 점검을 구분하되 무관한 절·매체는 로드하지 않는다. 관련 검색 기록이 있으면 채택·기각 근거와 미검증 조건도 입력에 포함한다. 검수 축을 추가하지 않는다.
   실행 가능한 UI·웹 코드 산출물은 [VISUAL-QUALITY.md](VISUAL-QUALITY.md)의 `실행 검증 로그`가 필수다. 로그 누락이나 가용한 검증의 미수행은 필수 증거 미검증으로 처리하고 해당 범위 PASS를 보류한다. 실제 과업 차단이 관찰되면 Critical로 구분한다. 비실행 산출물은 `검증 불가: 비실행 산출물`, 실행 환경·도구가 제한되면 시도한 방법·미검증 항목·제외 사유를 기록한다. 미검증을 기능 결함이나 통과로 추정하지 않는다.
3. A/B(리디자인 C)의 근거·판정을 별도 유지한다. 사용자에게는 상위 문제·해결 여부·남은 결정을 간단히 보고하고 상세 축별 기록을 연결한다. 한 축의 호평으로 다른 축의 미달을 덮지 않는다.
4. 범위 내 필수 Critical·Major는 해당 이슈를 만든 단계의 실행 주체가 수정한다. 위임할 수 없으면 주 에이전트가 수정한다. 단일 총예산 안에서 영향 기반 재검수를 수행하며 범위 밖 문제는 기록한다.
5. 최종 저장·내보내기한 파일을 검수 기록에 바인딩한 뒤 범위별 판정을 보고한다. 단순 작업은 기존 결과 로그를 갱신한다. 별도 최종 보고서가 필요한 전체 작업은 `outputs/final/YYYY-MM-DD_<project>_final.md`에 저장하되, 파일 저장 위치 자체를 통과 증거로 쓰지 않는다.

## 핵심 모드 조항

핵심 모드는 [RUN-BUDGET.md](RUN-BUDGET.md)의 경량 기본값을 따른다. 필수 기준·최종 증거·검수 방식의 정직한 표시는 동일하다.

- **최종 축 B**는 작업 위험·규모가 필요성을 뒷받침하고 위임 권한·도구가 있을 때 제작과 다른 실행 맥락 1개에 맡긴다(입력은 위 축 B 입력과 같고, 제작 과정의 자기 평가는 넘기지 않는다). 단순 audit·polish에 자동 위임하지 않는다. A/C는 오케스트레이터가 수행한다. 최종 검수 후 영향 변경이 있으면 기존 검수 맥락에서 관련 근거를 갱신하며 회차마다 새 역할을 만들지 않는다.
- 별도 실행 맥락이 실제로 축 B를 수행하지 않았으면 주 에이전트가 축 A와 축 B를 순서대로 기록한다. 축 B는 제작 맥락의 자기 평가를 재사용하지 않고 실물·렌더를 처음부터 다시 관찰한 뒤 원시 실행 로그와 대조한다. 보고 첫머리에 `재열람 기반 자체 검수(동일 맥락 검수)`를 표기한다.
- 두 축의 보고는 여전히 분리 작성한다. 핵심 모드도 같은 범위별 판정·필수 Critical·Major 해결·영향 기반 재검수·단일 총예산을 적용한다.
- 같은 산출물에서 Critical이 2회 연속 나오면 검수 단계를 전체 모드 수준으로 승격한다([RUN-BUDGET.md](RUN-BUDGET.md)의 단계별 승격).
