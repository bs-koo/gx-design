# UI 품질 — 화면 목적·진단·문구·예외 상태

웹·앱·데스크톱 UI의 브리프, 제작, 진단과 검수에 적용한다. BX·그래픽·영상만 만드는 작업에는 로드하지 않는다. Impeccable의 화면 목적 분류와 critique·audit·clarify·harden 방법을 gx-design의 기존 단계에 맞게 재구성했다. 외부 스킬 실행이나 별도 검수 축은 필요하지 않다.

**읽기 지도**

| 산출물 유형 | 읽을 절 | 건너뛸 절 |
|---|---|---|
| UI 브리프·전략(화면 목적·과업 정의) | §1 | §2~§4 |
| UI 제작 명세(코드 없음) | §1·§3·§4 표와 상태 문구 양식 | §2, §4 접근성 실행 체크·성능 조건부 규칙 |
| UI 코드 산출물 제작 | §1·§3·§4 전체 | §2 |
| gx-redesign 진단 | §1~§4 전체 | — |
| 검수 축 A(전략 일치) | §1 | §2~§4 |
| 검수 축 B(완성도)·축 C(개선 목표 달성) | §1~§4 전체 | — |

검수·진단 역할은 자기 축이 판정하는 절을 건너뛰지 않는다 — 축 B·축 C·진단은 이 문서 전체를 읽는다. `출처` 절은 모든 유형에서 건너뛴다.

## 1. 화면 목적을 먼저 정한다

브리프의 목표와 핵심 사용자 행동에서 화면별 주 목적을 도출한다. 프로젝트 업종만으로 정하지 않는다. 같은 제품의 소개 페이지와 관리 화면은 다른 목적을 가질 수 있다.

| 목적 | 성공을 판단할 기준 | 전략·제작에서 우선할 것 |
|---|---|---|
| 설득 | 방문자가 가치를 이해하고 필요한 행동을 선택한다 | 메시지 순서, 사실에 근거한 신뢰 정보, 행동의 결과가 분명한 CTA |
| 업무 수행 | 사용자가 과업을 정확하고 효율적으로 끝낸다 | 탐색·입력·비교의 효율, 적절한 정보 밀도, 상태와 복구 경로 |
| 읽기 | 내용을 찾아 이해할 수 있다 | 제목 체계, 탐색 구조, 읽기 폭, 본문과 보조 정보의 위계 |
| 감상 | 작품·결과물 자체를 충분히 볼 수 있다 | 콘텐츠의 크기와 맥락, 감상을 방해하지 않는 탐색·조작 |

브리프에는 `화면/경로 → 주 목적 → 핵심 과업 → 성공 기준`을 기록한다. 혼합 화면은 주 목적과 보조 목적을 적는다. 이미 확인 가능한 내용은 질문하지 않고, 선택에 따라 전략이 달라지는 불확실성만 기존 인터뷰 안에서 해소한다. 전체/핵심 **진행 모드**와 화면 목적은 별개다.

새 전략은 이 목적을 기준으로 구조·밀도·표현을 정한다. 예를 들어 업무 화면의 첫 영역은 업무 상태와 다음 과업을 우선하며, 업종이 기업용이라는 이유로 영업 문의 히어로를 추가하지 않는다. 확정된 브랜드·디자인 톤 기준과 사용자 요청이 표현 선택의 상위 기준이다.

### IA·과업 흐름 점검표

진단·검수는 화면 목적과 핵심 과업에 비추어 아래 항목을 확인하고, 제작 명세는 핵심 과업마다 각 항목의 설계 답을 적는다. 발견 사항은 §2 이슈 형식으로 기록한다.

| 항목 | 확인할 것 | 문제 신호(예) |
|---|---|---|
| 현재 위치 인지 | 제목·내비 활성 표시·경로 표시로 지금 어느 화면·단계·계층인지 알 수 있다 | 활성 표시 없음, 다른 화면과 같은 제목 |
| 다음·이전 단계 | 핵심 과업의 다음 행동과 되돌아갈 경로가 보이고, 되돌아가도 입력이 보존된다 | 완료 후 갈 곳 없음, 뒤로 가기에서 입력 손실 |
| 라벨 일관성 | 메뉴·버튼·페이지 제목·안내 문구가 같은 개념에 같은 용어를 쓴다(§3) | 메뉴 "주문 내역" → 페이지 제목 "구매 기록" |
| 막다른 길·우회 | 빈 결과·권한 부족·오류에서 빠져나갈 경로가 있고, 같은 목적지로 불필요하게 돌아가지 않는다 | 오류 화면에 행동 없음, 홈을 거쳐야 하는 이동 |
| 핵심 과업까지 단계 수 | 진입점에서 과업 완료까지 화면·조작 수를 실제 경로로 세어 브리프 성공 기준과 비교한다 | 기준 없이 "길다"고 단정 |

단계 수는 [VISUAL-QUALITY.md](VISUAL-QUALITY.md) 여정 로그의 `단계` 열에서 센다. 명세만 있으면 명세상 단계 수로 판단하고 실제 경로는 미검증으로 남긴다.

## 2. 진단과 검수는 시각·UX 판단과 구현 증거를 구분한다

gx-redesign 진단과 검수 축 B에서 아래 두 절을 구분해 기록한다. 기존 축 A(전략 일치), 축 C(개선 목표 달성)의 책임은 그대로 유지한다.

- **시각·UX 비평**: 실제 화면의 정보 위계, 핵심 행동의 발견 가능성, 비교·선택 부담, 간격·타이포·밀도, 문구와 상태 피드백을 화면 목적에 비추어 판단한다. 문제의 위치와 사용자 과업에 미치는 영향을 함께 적는다.
- **구현 점검**: 코드·실행 환경이 있을 때 키보드 경로와 포커스, 레이블·의미 구조, 실제 색 대비, 좁은 화면과 글자 확대, 테마 토큰, 로딩·오류·복구, 상호작용·성능을 검증한다. 제공된 플랫폼과 요청 범위에 해당하는 항목만 점검한다.

각 이슈는 `위치 → 재현 조건 → 근거(파일/캡처/측정/조작) → 사용자 영향 → Critical/Major/Minor → 수정 방향`으로 적는다. 진단표에는 관찰된 문제만 넣는다. 관찰된 증상은 **확인**, 그 원인 가설은 **추정**으로 구분한다. 직접 실행하지 못한 동작이나 측정하지 않은 성능은 **미검증**으로 검증 한계에 기록하며 문제라고 단정하지 않는다. 명세만 있으면 명세의 누락·모순을 판단하고 구현 검증은 미검증으로 남긴다. 범위 밖 항목은 내부 점검에서 해당 없음으로 제외하고 진단표를 채우지 않는다.

스크린샷은 레이아웃 증거이며 키보드·스크린리더·터치 제스처 동작의 증거가 아니다. 정적 detect의 지적 0건도 접근성·성능·전체 UX의 통과를 뜻하지 않는다. 증거 종류마다 쓸 수 있는 결론은 아래 허용표를 따른다. 도구 실행 실패는 검증 제약으로 기록하고, 실제 사용자 결함의 심각도와 구분한다. 진단 중에는 문제를 보고하고, 수정은 선택된 전략과 개선 허용 범위 안에서 수행한다.

### 증거 종류별 주장 허용표

| 증거 | 뒷받침할 수 있는 결론 | 뒷받침할 수 없는 결론 |
|---|---|---|
| 스크린샷·렌더 이미지 | 그 폭·상태에서 보이는 레이아웃·위계·간격·잘림·가림·문구 | 키보드·스크린리더·터치 동작, 상태 전환, 다른 폭·상태, 실제 대비(압축·오버레이 영향) |
| 코드 | 의미 구조·속성·토큰 사용·상태 분기의 존재 여부 | 실제 렌더 결과, 런타임 동작, 성능 |
| 실행(클릭·키보드) | 그 환경에서 과업 성공·실패, 포커스 이동, 오류·복구 결과 | 다른 기기·브라우저·보조기술의 결과, 사용자의 이해·선호 |
| 접근성 트리 | 조작 요소의 이름·역할·상태 노출 | 실제 스크린리더 낭독 경험, 시각 대비·레이아웃 |
| 측정 도구(detect·대비·성능 측정) | 그 도구가 그 조건에서 측정한 항목의 값 | 측정하지 않은 항목의 통과, 다른 기기·네트워크 조건의 값 |
| 사용자 자료(테스트·분석·문의 기록) | 자료가 다룬 과업·사용자군에서 관찰된 행동·빈도 | 자료 밖 과업·사용자군으로의 일반화, 원인 단정 |

한 결론에 필요한 증거가 없으면 해당 결론은 **미검증**이다. 여러 증거를 함께 쓰면 각 결론 옆에 어떤 증거로 확인했는지 적는다.

### 사용성 근거 구분

- 사용자 테스트·분석 자료가 제공되면 사용자 영향의 근거로 아래 요약을 먼저 적는다. 참여자는 수와 특성만 적고 개인 식별 정보는 옮기지 않는다.

  | 과업 | 참여자 | 관찰 | 성공/실패 |
  |---|---|---|---|
  | 상품을 장바구니에 담기 | 5명(첫 방문 모바일) | 3명이 옵션 선택 영역을 지나침 | 성공 2 / 실패 3 |

- 자료가 없으면 이슈의 `사용자 영향` 서술마다 `휴리스틱 추정`을 붙인다(예: `휴리스틱 추정: 첫 화면에서 주 CTA를 찾기 어려울 수 있다`). 이탈률·전환·만족도 같은 실사용자 결과로 쓰지 않는다.
- 자료와 휴리스틱을 섞을 때는 자료로 확인된 과업과 휴리스틱으로 판단한 과업을 행 단위로 구분한다.

## 3. UX 문구는 행동과 복구를 설명한다

제작에서 문구를 작성·수정할 때 관련 화면 흐름 전체를 확인한다.

- 버튼은 실행할 행동과 대상을 드러낸다. 삭제·해제 등 결과가 큰 행동은 대상과 결과를 설명하고, 복구 가능한 작업은 되돌리기 경로를 고려한다.
- 입력은 지속적으로 보이는 레이블과 필요한 형식·조건을 제공한다. 플레이스홀더만으로 항목을 설명하지 않는다.
- 오류는 실패한 작업과 사용자가 할 수 있는 다음 행동을 알려 준다. 원인이 확인되지 않으면 추측을 사실로 쓰지 않는다. 여러 입력 오류는 필드별 안내를 유지하고, 필요한 경우 연결된 오류 요약과 포커스 이동을 명세한다.
- 로딩은 무엇을 기다리는지, 빈 상태는 데이터가 없거나 검색 결과가 없는 이유와 가능한 다음 행동을 구분한다.
- 같은 개념에는 같은 용어를 사용한다. 확정된 제품 용어·브랜드 말투·사실·법적 의미를 임의로 바꾸지 않는다. 단순 문구 개선 중 새로운 기능·수치·효능을 추가하지 않는다.

### 상태 문구 양식

§4에서 선택한 상태는 명세에 아래 표로 적는다. 상태 ID는 실행 검증 로그·검수 지적이 같은 상태를 가리킬 때 쓴다.

| 상태 ID | 발생 조건 | 메시지 | 다음 행동 | 입력 보존 | 복구 확인 |
|---|---|---|---|---|---|
| S-01 | 결제 요청 시간 초과 | 결제를 완료하지 못했습니다. 입력한 내용은 그대로 있으니 다시 시도해 주세요. | 다시 시도 / 주문 내역 보기 | 배송지·옵션 유지 | 재시도 후 주문 1건만 생성 — 실행 검증 로그 참조 |

- 메시지는 위 원칙을 따른다 — 원인이 확인되지 않은 내용(예: "카드 한도 초과")을 쓰지 않는다.
- `입력 보존`은 유지되는 값과 지워지는 값을 적고, 해당 없으면 `해당 없음`.
- `복구 확인`은 실행해 확인한 결과와 그 로그 위치를 적는다. 실행하지 못했으면 `미검증`과 사유를 적는다.

## 4. 관련 예외를 제작 명세와 실물에서 확인한다

해당 과업에 실제로 발생할 수 있는 상태를 선택해 정의한다. 모든 화면에 같은 예외 목록을 강제하지 않는다.

| 조건 | 명세·구현에서 확인할 것 |
|---|---|
| 긴 한글·혼합 언어·큰 글자 | 레이블·버튼·표의 줄바꿈과 확장, 핵심 정보 접근, 고정 영역과 겹침 |
| 빈 데이터·검색 결과 없음 | 두 상태의 구분, 가능한 시작·필터 초기화 행동 |
| 느린 요청·실패·재시도 | 진행 상태, 입력 보존, 재시도 경로, 중복 제출 방지 |
| 권한 부족·읽기 전용 | 작업 가능 범위, 이유와 허용된 다음 행동 |
| 키보드·스크린리더·터치 | 조작 이름과 상태, 포커스 순서·복귀, 제스처 대안, 취소된 드래그의 상태 정리 |
| 모션 감소·지원 테마 | 상태 피드백을 유지하는 모션 대안, 실제 표시 색의 대비와 의미 |

명세에는 관련 상태의 문구·행동·레이아웃·수용 체크를 넣는다(문구는 §3 상태 문구 양식). UI 코드의 실행 확인과 기록은 [VISUAL-QUALITY.md](VISUAL-QUALITY.md)의 `실행 검증 로그` 규격을 따른다. 정상 경로와 관련 예외의 문구·복구 결과도 그 로그에 합류시키며, 별도 검증 루프를 만들지 않는다. 기존 품질 루프의 회차 안에서 발견 사항을 모아 수정하고, 변경된 과업만 재확인한다.

### 접근성 실행 체크

실행 가능한 UI 코드에서 위 키보드·스크린리더 조건을 아래 방법으로 확인하고 실행 검증 로그에 합류시킨다. 비실행 산출물은 명세에 각 항목의 의도를 적고 실행 확인은 미검증으로 남긴다.

| 체크 | 확인 방법 | 로그에 적을 것 |
|---|---|---|
| 접근성 트리 | 브라우저 접근성 스냅샷 또는 개발자 도구에서 조작 요소의 이름·역할·상태(선택·펼침·비활성·오류)를 확인한다 | 이름 없는 요소, 역할 불일치, 상태 미노출 목록 |
| 포커스 순서·복귀 | Tab·Shift+Tab 순서를 시각·과업 순서와 대조하고, 모달·메뉴·시트를 닫은 뒤 포커스가 연 요소로 돌아오는지 확인한다 | 순서 이탈 지점, 복귀 실패 위치 |
| 오류-입력 연결 | 오류 메시지가 해당 입력과 프로그램적으로 연결되고 입력에 오류 상태가 노출되며, 제출 실패 시 포커스가 첫 오류나 오류 요약으로 가는지 확인한다 | 연결되지 않은 오류, 포커스 이동 결과 |
| 확대 200% | 브라우저 확대 200%에서 내용·기능 손실, 두 방향 스크롤 발생, 고정 영역의 가림을 확인한다 | 손실·가림 위치와 폭 |

접근성 트리 확인은 이름·역할·상태 노출의 증거이며 스크린리더 실사용 경험의 통과가 아니다(§2 허용표). 스크린리더로 직접 확인하지 않았으면 그 범위를 미검증으로 적는다.

### 성능 조건부 규칙

성능은 아래 조건 중 하나일 때만 판정한다. 둘 다 아니면 성능 결론을 쓰지 않는다.

- 브리프·개선 브리프에 성능 목표가 있다.
- 실행 중 지연(늦은 첫 표시, 입력 반응 지연, 레이아웃 밀림)이 관찰됐다.

조건이 성립하면 측정 전에 계획을 정하고 같은 표에 결과를 기록한다.

| 지표 | 목표값 | 기기 | 네트워크 조건 | 측정 도구 | 결과 |
|---|---|---|---|---|---|
| LCP | 브리프 값(없으면 2.5초 이하 제안) | 중급 모바일 에뮬레이션 | 느린 4G 스로틀 | 브라우저 성능 패널 | 측정값 또는 미검증 |

- 웹 지표는 LCP(첫 주요 콘텐츠 표시)·INP(입력 반응)·CLS(레이아웃 밀림) 중 관찰된 문제나 목표에 맞는 것을 고른다. 브리프에 값이 없으면 Core Web Vitals의 `좋음` 기준(LCP 2.5초·INP 200ms·CLS 0.1 이하)을 출처와 함께 제안 값으로 쓴다. 네이티브·데스크톱은 플랫폼의 동등한 지표를 쓴다.
- 로컬·개발 환경 측정값은 측정 조건과 함께 적고 실서비스 사용자 값으로 일반화하지 않는다.
- 측정 도구·환경이 없으면 `미검증: 성능 측정 불가`와 관찰된 현상만 기록한다. 관찰된 지연은 **확인**, 그 원인은 **추정**으로 구분한다.
