# 개선 브리프 인터뷰 — 자산 인벤토리 + 모호함 제거 게이트

목표: 요청 대상 안의 자산을 파악하고, 목표·범위·불가침 영역의 미확정 필수 결정을 해소해 개선 브리프를 만든다. [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 결정 기록·답변 대기·승인 재사용이 단일 계약이다. 부분 수정에는 정해진 방향을, 점검에는 확정 점검 범위를 재사용한다.

## 절차

### 1. 자산 인벤토리 (질문 금지 영역)

미확정 핵심 의도가 있어 인터뷰가 필요한 경우에 수행한다. 요청 대상과 필요한 의존 자료부터 점진적으로 확인하고, 부족한 증거가 실제 결정을 막을 때만 범위를 넓힌다. 환경에서 확인 가능한 사실은 묻지 않는다. 중립적 사실 확인·현행 자산 열람은 가능하지만 미확정 방향을 전제한 조사 확대·시안·원본 수정은 하지 않는다. 명확한 점검·부분 수정은 SKILL의 직접 경로를 적용한다.

- 대상에 관련된 이전 브리프·전략·명세·final과 현재 참조하는 토큰·브랜드 가이드·DESIGN.md만 확인한다. 전체 outputs/ 열거와 무관한 화면 조사는 하지 않는다. 톤 강도·정본이 미확정일 때만 [DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md)의 해당 절을 읽는다.
- .pen 디자인 파일(pencil 도구로 열람), 프로토타입 코드, 스크린샷·이미지 자산
- 서비스가 배포되어 있으면 요청한 공개 화면과 필요한 의존 상태(가능한 브라우저 도구 사용 시)

자산 유형별 파악 방법:

- 문서(명세·토큰·가이드): 파일·이미지 보기 도구로 정독한다.
- .pen 파일: pencil 도구로 구조·스타일 값을 조회하고 스크린샷으로 렌더링을 확인한다.
- 프로토타입 코드: 코드를 정독하고, 실행 가능하면 실행해 실제 화면을 확인한다.
- 이미지·스크린샷: 파일·이미지 보기 도구로 열어 시각적으로 분석한다(레이아웃·컬러·타이포그래피·위계).
- 배포된 웹 화면: 대상 페이지·관련 상태의 스크린샷을 캡처해 분석한다. 인접 경로는 필요한 의존성이 있을 때만 연다.

**자산이 없거나 부족하면**: 이것은 환경에서 확인할 수 없는 정보다 — 첫 라운드 질문에 자료 요청을 포함한다
(현재 화면 스크린샷 첨부, 서비스 URL, 디자인 파일 경로, Figma 링크, 디자인 톤 기준 파일[DESIGN.md·브랜드 가이드] 중 무엇을 제공할 수 있는지). 톤 기준 파일 처리는 [../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md).
자료 없이 기억에 의한 묘사만으로 진단하지 않는다.

산출: 아래 양식의 자산 인벤토리. 이 인벤토리는 브리프에 그대로 들어간다.

| 자산 | 상태(발견/없음/접근 불가) | 시점 | 근거 |
|---|---|---|---|
| 디자인 토큰 `tokens/color.json` | 발견 | 파일 수정일 2026-08-02 | 경로, 정독 — 색 12개·의미 토큰 체계 |
| 배포 화면 `https://example.com/cart` | 접근 불가 | 2026-10-15 시도 | 로그인 필요 — 첫 라운드 자료 요청 |
| 브랜드 가이드·DESIGN.md | 없음 | 2026-10-15 조사 | outputs/·프로젝트 루트·docs/ 검색 결과 없음 |

- **발견**: 직접 열어 확인했다. 근거에 경로·확인 방법과 체계 요약(무엇이 있고 어떤 체계인지)을 적는다.
- **없음**: 조사한 위치에 없다. 근거에 조사한 위치를 적는다.
- **접근 불가**: 존재는 알지만 열 수 없다(권한·로그인·도구 없음). 위 자료 요청 대상이며 진단 근거로 쓰지 않는다.
- **시점**: 파일 수정일·캡처 일자·배포 화면 확인 일시. 확인할 수 없으면 `미상`.

### 2. 결정 트리 구축 (개선 전용)

- **상류**: 개선 계기(왜 지금 바꾸나 — 성과 지표 문제? 브랜드 변화? 경쟁 대응? 인상·취향?), 개선 목표와 성공 기준(무엇이 나아지면 성공인가), 개선 대상 범위(어떤 자산·화면·매체)
- **중류**: 유지 자산(불가침 — 로고·컬러·IA 등) vs 변경 허용 범위, 개선 강도 허용치(최소 수정 ~ 전면 리뉴얼), 제약(일정·개발 반영 범위·브랜드 규칙), 피할 것(개선 후에도 가지 말아야 할 룩 — [BRIEF-INTERVIEW.md](../gx-design/BRIEF-INTERVIEW.md) 2절 "피할 것" 문항 준용)
- **하류**: 레퍼런스·선호 톤, 매체별 세부 형식

UX/UI가 포함되면 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §1에 따라 현행 화면의 목적·핵심 과업·성공 기준을 기록한다. 목적 변경이 요청되지 않았으면 기존 과업을 유지하고, 인상 개선을 이유로 새 기능·영업 메시지를 추가하지 않는다.
현행 화면의 **핵심 여정**(검증 시나리오 — 예: 메인 → 상세 → 장바구니)도 함께 기록한다. 배포 화면·프로토타입에서 확인되면 직접 적고, 모르면 화면 목적 질문과 같은 라운드에 묻는다. 진단의 실행 검증과 검수의 회귀 확인이 같은 여정을 쓴다.

"요즘 느낌으로"류의 모호어는 하류(취향)가 아니라 상류에서 먼저 분해한다 —
무엇이 낡았다고 느끼는지, 그래서 무엇을 달성하고 싶은지가 레퍼런스 선택보다 먼저다.

### 성공 기준 표

상류에서 확정한 성공 기준은 아래 표로 기록한다. UX/UI의 화면별 성공 기준도 별도 목록이 아니라 이 표의 행으로 적는다. 검수 축 C는 같은 관찰법으로 재측정해 `결과` 열을 채운다([creative-review](../creative-review/SKILL.md) 개선 목표 달성).

| 기준 ID | 기준선(현재 관찰값) | 목표값/관찰법 | 측정 시점 | 결과 |
|---|---|---|---|---|
| G-01 모바일 장바구니 담기 | 375×812에서 옵션 시트가 하단 바에 가려 담기 불가(J-01-375) | 같은 경로 J-01-375로 담기 완료 · 단계 수 4 이하 | 진단(기준선) / 검수 축 C | (검수에서 기록) |
| G-02 첫 화면 주 행동 | 데스크톱 첫 화면에 같은 크기 CTA 3개 | 첫 화면 주 CTA 1개, 보조 행동은 시각 위계가 낮음 — 1440×900 캡처 비교 | 진단 / 검수 축 C | (검수에서 기록) |
| G-03 "세련되게" | 정성 기준 | 사용자가 before/after 캡처를 보고 확인 | 검수 후 사용자 확인 | (검수에서 기록) |

- **기준선**은 인벤토리·진단에서 실제로 관찰한 값이다. 인벤토리로 확인되는 값은 묻지 않는다. 아직 관찰하지 못했으면 `미측정 — 진단에서 측정`으로 두고, 진단에서 같은 관찰법으로 채운다.
- **목표값/관찰법**은 수치 목표나 재현 가능한 관찰 방법(폭·경로 ID·도구·조건)을 적는다. 재측정 때 관찰법을 바꾸지 않는다.
- **측정 시점**은 이 작업 안의 시점(진단·검수 축 C)과 작업 밖 시점(출시 후)을 구분한다. 전환율·이탈률처럼 출시 후에만 측정할 수 있는 목표는 `출시 후`로 적고, 이 작업에서는 달성을 주장하지 않는다.
- **정성 기준**: 인상 목표("세련되게", "요즘 느낌으로")는 상류 분해 결과를 관찰 가능한 대리 기준으로 번역한다(예: accent 1개·[VISUAL-CRAFT.md](../gx-design/VISUAL-CRAFT.md) §1 기본 룩 비해당·타이포 위계 3단계 이하). 번역할 수 없거나 사용자가 번역을 원하지 않으면 기준선 칸에 `정성 기준`이라고 표기하고 관찰법에 판정 주체(사용자 확인)를 적는다. 정성 기준을 수치 달성처럼 보고하지 않는다.

### 점검 전용 범위 — 경량 개선 브리프

gx-redesign이 **점검 전용**이면([SKILL.md](SKILL.md) 모드 결정) 1절에서 요청 대상 안의 인벤토리를 수행하고 아래 필수 항목만 확정한다. 열린 슬롯만 묻고 필수 응답을 기다린다([HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#질문-슬롯-산정표)):

- 점검 대상(복수 선택 가능함을 밝힌다): 시각·UX / 모션 / AI 티 / 실행 여정
- 대상 화면·URL(인벤토리로 확인되면 묻지 않는다)
- 기기(모바일·데스크톱·둘 다 — 인벤토리로 확인되면 묻지 않는다)
- 실행 여정이 대상이면 핵심 여정

개선 계기·강도·유지 자산은 묻지 않는다. 요청 또는 인벤토리로 점검 대상·화면/URL·기기와 해당 시 핵심 여정이 정해졌으면 재승인 없이 경량 브리프를 진단 보고 머리에 `[요청에서 확정]`으로 표시한다. 미정인 필수 항목만 질문한다. 점검 보고로 완료하며 필수 이어가기 질문은 하지 않는다. 후속 수정이 명시 요청되면 기존 진단과 결정은 재사용하고 새 범위의 미정 항목만 확인한다.

### 특정 지적·부분 다듬기

대상·보존 조건·원하는 결과가 요청에서 확정됐으면 해당 범위의 인벤토리·진단·변경 근거를 기록하고 수정·관련 검증으로 간다. 전체 리서치·전략 3안·브리프 재승인을 추가하지 않는다. 대상이 여러 개이거나 의미·동작·브랜드 변경 허용치가 모호하면 그 결정만 질문한다. polish의 진단 ID 집합은 SKILL.md의 계약대로 사용자에게 보인 범위를 명시 응답으로 확정하고, ID 생략을 전체 수정으로 해석하지 않는다.

### 3~7. 라운드 규칙

[../gx-design/BRIEF-INTERVIEW.md](../gx-design/BRIEF-INTERVIEW.md)의 3~7절 규칙을 그대로 따른다:
frontier 계산(결과를 바꾸는 사용자 결정만, 의존 질문은 다음 라운드) / 라운드 실행(HOST-COMPAT의 질문 품질·필수 대기) / 트리 갱신(총량 무제한, 부분 답변은 해당 결정만) / 탈출구(현재 범위의 명시 위임, [가정] 표기, 단독 "멈춰"는 중단) / 종료 게이트(필요한 새 승인 또는 기존 승인·요청 재사용 → 저장).
라운드 규칙은 모드와 무관하게 같다 — 핵심 모드도 frontier가 빌 때까지 묻는다. 첫 라운드 슬롯 순서는 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#질문-슬롯-산정표)의 질문 슬롯 산정표(리디자인 행)를 따른다. 인벤토리로 이미 확인된 사실(대상·기기 등)은 슬롯을 쓰지 않고 묻지 않는다.
첫 라운드 머리말의 **요청 해석 카드**도 준용한다 — 슬롯은 `무엇(개선 대상) / 누구·목적(개선 계기) / 피할 것 / 기준 자료(DESIGN.md·레퍼런스·인벤토리) / 범위·기기`. 인벤토리로 채워진 칸은 ✓로 보여 주고 묻지 않는다.
디자인 톤 기준 자료가 실제 제약을 정하는 데 필요할 때만 첨부를 요청한다. 기성 DESIGN.md(designmd.co, awesome-design-md)는 선택적 출발점이며 기존 보존 조건을 바꾸지 않는다. 카탈로그는 soft, 자신의 확정 브랜드는 hard이고 명시된 강도를 재질문하지 않는다([DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §2·3).

저장 경로: `outputs/brief/YYYY-MM-DD_<project>_redesign-brief.md`

## 개선 브리프 양식

- 프로젝트명
- 개선 대상 자산 인벤토리 (`자산 | 상태(발견/없음/접근 불가) | 시점 | 근거`)
- 개선 계기와 목표
- 성공 기준 표 (`기준 ID | 기준선(현재 관찰값) | 목표값/관찰법 | 측정 시점 | 결과` — 결과 열은 검수에서 채운다)
- 개선 범위
- 화면별 목적·핵심 과업 (UX/UI일 때 — ../gx-design/UI-QUALITY.md §1. 화면별 성공 기준은 성공 기준 표의 기준 ID로 연결)
- 핵심 여정(검증 시나리오) (UX/UI일 때 — 대상 기기·경로 ID 포함, ../gx-design/VISUAL-QUALITY.md 여정 로그)
- 유지 자산 (불가침)
- 변경 허용 범위
- 개선 강도 허용치
- 제약 조건
- 레퍼런스
- 피할 것 (없으면 "지정 없음")
- 디자인 톤 기준 (있을 때: 강도[hard/soft]·팔레트·타이포·톤 요약·원본 파일 경로 — ../gx-design/DESIGN-TONE-ANCHOR.md)
- [가정] 목록 (명시 위임 시, 근거·적용 범위 포함)
- 결정 기록 (`id / value / status / source / scope-version / dependencies` — 기존 기록 안에 유지)

점검 전용 경량 브리프는 프로젝트명 / 자산 인벤토리 / 점검 대상 / 대상 화면·URL / 기기 / 핵심 여정(실행 여정 대상일 때) / 디자인 톤 기준(있을 때)만 적는다. 저장 경로는 같다.
