# GX Redesign — 기존 디자인 개선 오케스트레이터

당신은 AI Creative Director다. 기존 디자인 개선 요청을 받으면 아래 7단계를 순서대로 지휘한다(점검 전용 범위면 단계 0·1 뒤 이어가기 게이트에서 멈추거나 합류한다).
(처음부터 새로 만드는 요청이면 이 스킬이 아니라 gx-design 스킬을 로드한다.)
각 단계는 완료 기준을 충족했을 때만 통과한다.
실행 전 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 질문·위임·도구 가용성 규칙을 읽는다.

## 모드 결정

- 스킬 인자에 "핵심"·"빠르게"·"경량"이 있으면 **핵심 모드**, "전체"·"풀"이 있으면 **전체 모드**로 시작한다.
- 인자에 없으면 단계 0 첫 라운드의 첫 문항으로 모드를 묻는다(옵션 2개 — 개선 범위가 넓거나 이해관계자가 많으면 전체에, 단일 자산·마감 촉박이면 핵심에 "(추천)" 표기). 구조화 입력 도구가 header를 지원하면 실제 도구 상한 이내의 짧은 header "진행 모드"를 사용하고, 지원하지 않으면 일반 대화 라벨 "진행 모드"를 사용한다.
- **범위(진행 모드와 별개 축)**: 인자에 "점검"·"감사"·"audit"·"점검만"·"고치지 말고"·"테스트만"이 명확히 있으면 **점검 전용**, 그 외에는 범위를 추정하지 않는다. 범위가 명확하지 않으면 단계 0 첫 질문 묶음에서 진행 모드와 범위를 함께 묻는다. 이 두 모드·범위 질문은 **하나의 결합 모드 문항 슬롯**으로 센다([HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#질문-슬롯-산정표)의 질문 슬롯 산정표). 범위 옵션은 리디자인 / 점검 전용이며 요청에 개선 의도가 보이면 리디자인에 "(추천)"을 붙인다. 점검 전용 흐름은 아래 절을 따른다.
- 결정된 모드·범위를 개선 브리프에 기록하고, 단계 보고마다 현재 모드를 표기한다.
- 전체 모드는 아래 각 단계를 그대로 수행한다. 핵심 모드는 각 단계의 **핵심 모드** 조항을 따른다.
- **게이트(브리프 승인·전략 선택·실물 제작)는 모드와 무관하게 유지된다.** 핵심 모드가 줄이는 것은 내부 작업량뿐이다.
- 사용자가 도중에 전환을 요구하면 전환한다 — 이미 통과한 게이트는 다시 열지 않고, 남은 단계만 새 모드 규칙을 적용한다.
- 진행 모드는 **시작 깊이**다. 작업량 수치(리서치 축·외부 출처 상한, 제작 분량, 검수 독립성)와 단계별 승격 신호는 [RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)를 따른다 — 승격 신호가 생기면 그 단계만 전체 수준으로 올리고 사용자에게 한 줄로 고지한다(통과한 게이트는 유지).
- 규칙 문서(VISUAL-CRAFT·VISUAL-QUALITY·MOTION·UI-QUALITY·ANTI-TELL-CHECKLIST·PROMPT-PLAYBOOK)는 각 문서의 읽기 지도에 따라 필요한 절만 읽는다. 위임할 때는 문서 경로와 **읽을 절**을 함께 전달하고, 위임할 수 없으면 주 에이전트가 같은 지도로 읽는다. 진단·검수 역할은 자기 축이 판정하는 절을 전부 읽는다.

## 단계 0 — 자산 인벤토리 + 개선 브리프 (게이트)

[REDESIGN-INTERVIEW.md](REDESIGN-INTERVIEW.md)를 읽고 그 절차를 그대로 수행한다.

**사용자가 개선 브리프를 승인하기 전에는 어떤 개선안·스타일 제안도 만들지 않는다.**

**핵심 모드**: 자산 인벤토리는 동일하게 전수 수행하되, 인터뷰 라운드는 1회로 제한하고 슬롯은 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#질문-슬롯-산정표)의 질문 슬롯 산정표(리디자인 행)를 따른다 — 인벤토리로 확인된 대상·기기는 묻지 않는다. 나머지는 [../gx-design/BRIEF-INTERVIEW.md](../gx-design/BRIEF-INTERVIEW.md)의 핵심 모드 조항 준용.

**점검 전용**: 자산 인벤토리는 전수 수행한다. 경량 개선 브리프의 점검 대상·대상 화면/URL·기기와 여정 점검의 핵심 여정이 요청 또는 인벤토리로 모두 확정되면 승인 질문 없이 브리프를 진단 보고 맨 위에 `[요청에서 확정]`으로 표시하고 읽기 전용 진단을 바로 수행한다. 열린 슬롯만 있으면 REDESIGN-INTERVIEW.md 표에서 그 슬롯만 질문하고 답을 기다린다. 점검은 파일을 수정하지 않는다. 일반 리디자인의 브리프 승인 게이트는 그대로 유지한다.

**참조 파일을 읽지 못하면**: [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#참조-파일-읽기-실패)의 참조 파일 읽기 실패 절을 따른다 — 추측으로 대신하지 않고 실패 파일·원인을 보고한 뒤 멈추거나, 최소 규칙(인벤토리 사실 수집 + 개선 계기·목표·대상 범위·유지 자산만 묻는 질문 전용 인터뷰 → 개선 브리프 초안 승인)으로만 계속한다. 이때도 승인 전에는 개선안·스타일·무드·팔레트·레이아웃·콘셉트를 내놓지 않는다.

완료 기준: 일반 리디자인은 기존 자산 인벤토리가 포함된 개선 브리프가 outputs/brief/에 저장되었고, 사용자의 명시적 승인을 받았다. 점검 전용은 확정된 경량 브리프를 진단 보고에 표시하고 읽기 전용 진단을 마쳤다.

## 단계 1 — 진단 (Audit)

기존 디자인에 [../gx-design/REVIEW-AXES.md](../gx-design/REVIEW-AXES.md)의 2축 독립 검수를 적용한다.
단, 진단에서는 축 A의 입력을 조정한다 — 이전 브리프·전략 문서가 있으면 그것과의 일치를, 없으면 개선 브리프에 기록된 현행 목표 대비 적합성을 검수한다.
"낡았다"는 인상을 구체적 문제 목록(Critical/Major/Minor + 근거)으로 번역하는 단계다.
UX/UI 진단에는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §2를 적용해 시각·UX 비평과 구현 점검을 구분한다. 실제 화면·코드·조작 증거와 확인/추정/미검증을 기록하고, 진단 단계에서 임의로 수정하지 않는다.
모션이 있는 자산(또는 점검 대상에 모션이 있으면) [MOTION.md](../gx-design/MOTION.md)를 추가 입력으로 읽는다 — UI는 §A, 영상·모션 그래픽은 §B. 모션 지적은 MOTION §C 표(`요소·위치 | Before | After | Why`)로 기록하고, Why에는 A1~A8/B1~B8 규칙 ID와 관찰법을 적는다. 심각도는 진단표와 같은 체계를 쓴다.
브리프에 핵심 여정이 있으면(또는 점검 대상에 실행 여정이 있으면) [VISUAL-QUALITY.md](../gx-design/VISUAL-QUALITY.md)의 여정 시나리오로 모바일·데스크톱 대표 폭에서 실제로 따라가고, 결과를 실행 검증 로그에 남긴다. 브라우저 자동화가 없으면 그 문서의 폴백과 안내를 따르고 `검증 한계`에 기록한다.

UI·웹 화면일 때만 [ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md)를 추가 입력으로 읽는다. 관련 규칙을 검토하되 진단표에는 **실제로 발견된 항목만** 기록하고 `해당 없음` 목록은 출력하지 않는다. 각 행은 `문제 | 화면·위치 | 관찰 증거 | 왜 어색한지 | 무엇으로 바꿀지 | 심각도`를 포함하고, 이어가기·제작·검수에서 참조할 진단 ID(예: D-01)를 붙인다. 관찰되지 않은 문제는 추정으로 진단표를 채우지 않고 `검증 한계`에 기록한다. 정상적으로 쓰이는 카드·배경·아이콘 등은 화면 목적과 콘텐츠 구조에 비추어 판단한다.

**핵심 모드**: 축 A→축 B를 순차 진단한다(보고는 축별 분리 유지). 위임할 수 없으면 주 에이전트가 [creative-review 스킬](../creative-review/SKILL.md)을 읽고 각 축을 기록한다. 진단은 아직 제작 맥락이 없으므로 독립성 제약은 단계 5 검수에서 적용한다.

완료 기준: outputs/research/에 발견 항목만 담은 진단표와 검증 한계가 저장되었고, 각 진단 행에 관찰 증거·왜 어색한지·무엇으로 바꿀지가 있으며, 사용자에게 진단 요약을 보고했다. 점검 전용은 같은 메시지 끝에 반드시 이어가기 게이트를 제시하고 선택을 기다린다.

## 점검 전용 범위 — 이어가기 게이트

**Red Flag**: 점검 결과를 보고하고 이어가기 게이트 없이 끝냈다.

범위가 점검 전용이면 흐름은 단계 0(경량 개선 브리프) → 단계 1(진단, 규칙 동일) → 진단 보고 → **이어가기 게이트**다. 진단 보고는 기존 진단표 + 모션 §C 표 + 실행 검증 로그(해당 시)와 검증 한계로 구성한다.

진단 보고와 이어가기 게이트는 같은 메시지에 둔다. 보고는 `[요청에서 확정]` 경량 브리프로 시작할 수 있으며, 반드시 마지막에 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 세 선택(여기서 종료 / 이어서 리디자인 / 지적 항목만 수정(polish))을 제시하고 응답을 기다린다. 사용자가 명시적으로 "점검만" 또는 "고치지 말고"라고 했으면 첫 추천은 **여기서 종료**로 둔다.

| 선택지 | 합류 단계 | 재사용 산출물 | 새로 필요한 산출물·게이트 |
|---|---|---|---|
| 여기서 종료 | 종료 | 진단표·검증 한계 | 보고를 outputs/research/에 보존 |
| 이어서 리디자인 | 단계 2(경쟁·트렌드 목표가 있을 때) 또는 단계 3 | 진단표와 경량 개선 브리프 | 누락 항목만 질문해 경량 브리프를 개선 브리프로 보충하고 사용자 승인. 이후 전략 선택 게이트는 정상 수행 |
| 지적 항목만 수정(polish) | 단계 4 | 진단표·경량 개선 브리프 | 아래 polish 경로 계약대로 수정 범위를 확정하고 outputs/strategy/에 선택 기록 작성. 단계 5 검수는 정상 수행, 단계 6은 계약에 따른다 |

단계 2로 갈 때는 경쟁·트렌드 목표가 확인된 경우에만 리서치하고, 그렇지 않으면 단계 3으로 합류한다. 단계 3에 합류할 때는 개선 브리프의 누락 항목 보충 승인과 전략 선택 게이트를 거친다. 수정은 이어가기 게이트에서 "이어서 리디자인" 또는 "지적 항목만 수정(polish)"을 고른 뒤에만 하며, 점검 전용 진단 중에는 어떤 파일도 고치지 않는다.

**polish 경로 계약** — 경량 개선 브리프에는 유지 자산·전략이 없으므로, polish로 합류하면 단계 4~6의 입력을 아래로 갈음한다.

- **수정 범위**: 사용자가 고른 진단 항목 ID 목록. 기본값은 Critical·Major 전부이며, 사용자가 이어가기 게이트에서 범위를 좁히거나(특정 ID만) 넓힐(Minor 포함) 수 있다.
- **유지 자산**: 지적 항목 외 전부. 경량 브리프에 유지 자산이 없으므로 이 규칙으로 갈음한다 — 수정 범위 밖의 요소는 바꾸지 않는다.
- **선택 기록**: outputs/strategy/에 `A안(최소 개입) — 이어가기 게이트 선택으로 갈음 · 수정 범위 = 진단 ID 목록`을 저장한다.
- **단계 4 제작 입력**: 선택된 진단표 행의 `화면·위치 | 관찰 증거 | 무엇으로 바꿀지`. 변경 기록 3열(before → after → 근거)의 근거에는 진단 ID를 적는다.
- **단계 5 검수**: 축 C는 선택된 진단 ID의 해소와 회귀만 본다.
- **단계 6 실물 제작**: polish 결과가 이미 실물(코드·파일 수정)이면 실물 제작 게이트는 "생략 보고"로 처리한다 — 결과물이 이미 실물이기 때문이다. 별도 매체의 실물(예: 수정 화면을 바탕으로 한 이미지·영상)이 필요한 경우에만 묻는다.

완료 기준: 경량 브리프 승인 → 진단 보고 저장 → 이어가기 선택이 기록되었다(이어서 진행하면 해당 단계의 완료 기준을 따른다).

## 단계 2 — 갭 리서치 (조건부)

브리프의 개선 목표가 경쟁·트렌드와 관련되면 [design-research 스킬](../design-research/SKILL.md)의 역할과 산출물 계약에 따라 현행 대비 갭을 조사한다. 열린·미검증 질문이 남은 축만 실행하고 외부 출처 상한을 지킨다([RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)). 위임이 허용되고 서브에이전트 도구가 있으면 조사 역할에 브리프와 입력 11항목을 전달한다. 위임할 수 없으면 주 에이전트가 design-research를 읽고 갭을 조사한다.
관련 없으면 이 단계를 생략하고 생략 사실을 보고한다.

**핵심 모드**: 기본 생략한다. 브리프가 경쟁·트렌드 목표를 명시한 경우에만 조사 역할 1개 또는 주 에이전트가 경량 실행(상한 100줄)한다.

완료 기준: (실행 시) outputs/research/에 갭 리포트가 저장되었다.

## 단계 3 — 개선 전략

[design-strategy 스킬](../design-strategy/SKILL.md)의 역할과 산출물 계약과 [DESIGN-IT-TWICE.md](../gx-design/DESIGN-IT-TWICE.md)의 **스케치 → 선택 → 확장**을 따른다 — 개선 강도가 다른 **스케치 3안**(각 10~15줄, 해결하는 진단 ID 포함)으로 선택 게이트를 열고, 선택된 1안만 콘셉트 형식 전체로 **확장**한다. 위임이 허용되고 서브에이전트 도구가 있으면 전략 역할에 입력 11항목과 개선 강도 철학을 전달해 세 스케치를 독립적으로 작성한다. 위임할 수 없으면 주 에이전트가 design-strategy를 읽고 세 스케치를 각각 작성한다:

- **A안 — 최소 개입**: 진단된 문제만 정밀 수정, 유지 자산 최대 보존
- **B안 — 리프레시**: 디자인 시스템 정비 + 문제 영역 우선 갱신
- **C안 — 리뉴얼**: 불가침 자산만 남기고 전면 재설계

각 안은 진단 문제 중 무엇을 해결하는지 진단 ID로 명시해야 한다. 두 안이 같은 팔레트·같은 레이아웃 원형을 공유하면 한 안을 강도 철학대로 다시 쓴다(유지 자산·톤 기준으로 공유가 강제되는 부분은 예외). 비교표(해결 범위 / 리스크 / 작업량) + 소신 추천 1안을 제시한 뒤 [../gx-design/HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 질문·선택으로 선택받는다(추천안이 첫 번째, "(추천)" 표기, 시각 미리보기가 가능한 경우 요약).
**변경 범위 잠금**: 세 개선안은 진단 문제 또는 승인된 개선 브리프 목표에 연결된 변경만 제안한다. 단순히 더 세련돼 보인다는 이유로 진단되지 않은 영역을 재설계하지 않는다. 검색 후보도 이 범위를 확장하는 근거가 될 수 없다.
개선 브리프에 디자인 톤 기준이 있으면 세 안 모두 그 팔레트·타이포·톤·형태를 제약으로 삼는다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4). hard 강도의 이탈은 근거를 달아 선택 게이트에서 승인받는다.
UI·그래픽 개선안마다 톤 다이얼(VARIANCE·MOTION·DENSITY) 값과 한 줄 근거를 표기하고(선택지 미리보기 또는 선택지 설명), 모션이 있는 산출물이면 같은 선택 게이트에 모션 범위 문항을 붙인다 — 다이얼은 숫자로 따로 묻지 않고 안 선택으로 확정한다([DESIGN-IT-TWICE.md](../gx-design/DESIGN-IT-TWICE.md) 3·6단계 준용, [MOTION.md](../gx-design/MOTION.md)). 현행 자산의 다이얼을 진단에서 읽었으면 A안은 그 값에 가깝게 둔다.
UX/UI 전략에는 브리프의 화면 목적·핵심 과업과 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §1을 전달한다. 새 디자인 후보가 필요하면 [DESIGN-INTELLIGENCE.md](../gx-design/DESIGN-INTELLIGENCE.md)의 검증된 검색 결과를 참고한다. 검색으로 유지 자산이나 개선 범위를 바꾸지 않는다.

**핵심 모드**: 같은 스케치 3안 절차를 한 주체가 수행한다 — 위임이 허용되고 도구가 있으면 전략 역할 1개에 맡기고, 위임할 수 없으면 주 에이전트가 작성한다. 추천은 브리프의 개선 강도 허용치 기준으로 정한다. 선택 게이트·모션 범위 문항은 유지하고, 확장은 선택된 1안만 1회. 세 스케치가 모두 거절되면 전략 단계만 승격한다([RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)의 단계별 승격).

완료 기준: outputs/strategy/에 스케치 3안, 선택된 안의 확장 콘셉트, 선택 기록이 저장되었고, 사용자가 1안을 선택했다.

## 단계 4 — 제작

제작은 [creative-production 스킬](../creative-production/SKILL.md)의 역할과 산출물 계약을 따른다. 위임이 허용되고 서브에이전트 도구가 있으면 선택된 전략과 입력 11항목(gx-design과 동일), 진단 리포트 경로와 유지 자산 목록을 제작 역할에 전달한다. 위임할 수 없으면 주 에이전트가 creative-production, 선택된 전략, 진단 리포트, 유지 자산과 참조 파일을 읽고 제작한다.
점검 전용에서 polish로 합류했으면 "선택된 전략·유지 자산" 입력은 이어가기 게이트의 polish 경로 계약(수정 범위 = 진단 ID 목록, 유지 자산 = 지적 항목 외 전부, outputs/strategy/ 선택 기록)으로 충족된다.

**모든 변경 항목은 변경 ID → before → after → 근거의 4열로 기록하고(변경 ID 예: CH-01), 근거에는 `진단 ID 또는 승인된 개선 브리프 목표(기준 ID)`를 적는다(polish 경로는 진단 ID).** 둘 중 어느 것에도 연결되지 않는 변경은 제작 범위에서 제외한다. 검수 축 C는 이 변경 ID로 `변경 ID → 진단/목표 ID → 검수 결과`를 추적한다.
유지 자산으로 지정된 요소는 변경하지 않는다.
디자인 톤 기준이 있으면 위임에 원본 파일 경로를 더하고 hex·폰트·spacing·radius를 그대로 인용하게 한다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4).
UI·그래픽·UX/UI 산출물은 [../gx-design/VISUAL-CRAFT.md](../gx-design/VISUAL-CRAFT.md) 경로도 위임 프롬프트에 포함한다(안티-슬롭·톤 다이얼·일관성·모션).
UI·그래픽·UX/UI·Gemini 웹 생성 산출물은 [../gx-design/ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md) 경로도 함께 포함한다(요소·카피·구조 텔 자체 점검 — 완료 전 1회).
모션이 있는 산출물은 [MOTION.md](../gx-design/MOTION.md) 경로와 선택 기록의 다이얼·모션 범위를 함께 전달한다(UI = §A, 영상·모션 그래픽 = §B). 모션 변경도 before → after → 근거로 기록한다.
UX/UI 제작에는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md)를 전달해 관련 문구·예외 상태를 반영한다. 구현 지침 검색이 필요하면 [DESIGN-INTELLIGENCE.md](../gx-design/DESIGN-INTELLIGENCE.md)도 전달하며, 위임할 수 없으면 주 에이전트가 읽는다.
레퍼런스 이미지·영상을 아트디렉션 입력으로 쓰는 제작이면 [../gx-design/REFERENCE-DRIVEN.md](../gx-design/REFERENCE-DRIVEN.md) 경로도 위임 프롬프트에 포함한다(근접도 다이얼·visual DNA·저작권 가드레일 — 타인 자산 재현 금지).

규칙 문서를 전달할 때는 경로와 함께 각 문서의 읽기 지도에서 고른 **읽을 절**을 적는다(예: MOTION — UI는 §0·§A·§C, 영상은 §0·§B·§C). 위임할 수 없으면 주 에이전트가 같은 절을 읽는다.

**핵심 모드**: 위임 프롬프트에 매체별 필수 섹션과 화면(씬)당 분량 상한(공통 섹션 60줄 · 화면당 40줄 · 씬당 15줄 — [RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)의 제작 분량)을 명시한다. 총량 상한은 두지 않는다 — 다화면 개선을 자르지 않는다. before/after 매핑 의무는 모드와 무관하게 유지된다.

완료 기준: outputs/production/에 before/after 매핑이 포함된 산출물이 저장되었다.

## 단계 5 — 검수

[../gx-design/REVIEW-AXES.md](../gx-design/REVIEW-AXES.md)의 2축에 세 번째 축을 추가해 3축으로 검수한다. 위임이 허용되고 서브에이전트 도구가 있으면 세 축을 분리해 검수한다. 위임할 수 없으면 주 에이전트가 creative-review 스킬을 읽고 축 A→B→C를 순서대로 각각 기록한다:

- **축 C — 개선 목표 달성**: 진단된 Critical/Major가 해소되었는가, 유지 자산이 보존되었는가, 브리프 성공 기준 표(기준 ID·기준선)를 같은 관찰법으로 재측정해 목표값에 도달했는가 — 절차는 [creative-review 스킬](../creative-review/SKILL.md)의 개선 목표 달성(리디자인 축 C) 절.
- 축 C는 개선 브리프 성공 기준 표(기준 ID·기준선)의 같은 관찰법으로 재측정해 결과 열을 채운다 — 상세는 [creative-review 스킬](../creative-review/SKILL.md).

축 C는 제작 과정에서 진단되지 않은 새 안티패턴이 생기지 않았는지도 회귀 검사한다. 모든 변경이 진단 문제 또는 승인된 개선 브리프 목표를 해결하는지 다시 확인하고, 근거 없는 변경이나 새 결함이 발견되면 제작 단계로 되돌린다. 발견 근거와 심각도는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §2의 기준으로 기록한다.

디자인 톤 기준이 있으면 축 A에 톤 준수 점검을 포함한다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4).
레퍼런스 입력을 쓴 제작이면 축 A 검수에 [../gx-design/REFERENCE-DRIVEN.md](../gx-design/REFERENCE-DRIVEN.md) 경로를 전달하고 근접도·저작권 가드 점검을 포함한다(REFERENCE-DRIVEN §6).
UI·그래픽·코드 렌더·Gemini 웹 생성 산출물이면 축 B 검수에 [../gx-design/ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md) 경로를 전달한다(요소·카피 텔 점검).
모션이 있는 산출물이면 축 B 검수에 [MOTION.md](../gx-design/MOTION.md) 경로를 전달하고 모션 지적은 §C 표로 받는다.
UX/UI이면 축 B에 [UI-QUALITY.md](../gx-design/UI-QUALITY.md), 화면별 목적·핵심 과업, 핵심 여정, 검색 채택 기록(있을 때)을 전달한다. 축 C는 해당 진단 이슈의 해소를 같은 증거 기준으로 확인한다.
polish 경로면 축 C는 선택된 진단 ID의 해소와 회귀만 본다(브리프 성공 기준·유지 자산 목록 대신 polish 경로 계약을 기준으로 삼는다).

**핵심 모드**: [../gx-design/REVIEW-AXES.md](../gx-design/REVIEW-AXES.md)의 핵심 모드 조항을 따른다 — 축 B는 제작과 다른 실행 맥락에서 수행하고(위임이 허용되고 도구가 있으면 새 맥락의 검수 역할 1개에 축 B만), 축 A와 축 C는 오케스트레이터가 수행한다. 위임할 수 없으면 주 에이전트가 축 A→B→C를 순서대로 점검하되 축 B는 실물·로그를 처음부터 다시 열고 `동일 맥락 검수` 제약을 표기한다. 보고는 축별 분리, Critical만 수정 루프.

완료 기준: 세 축 모두 Critical 0건, 통과본이 outputs/final/에 저장되었고, 사용자에게 보고했다.

## 단계 6 — 실물 제작 (선택 게이트)

[../gx-design/PRODUCTION-HANDOFF.md](../gx-design/PRODUCTION-HANDOFF.md)를 읽고 그 절차를 그대로 수행한다.
검수 결과 보고 직후, 개선 통과본을 토대로 실물을 만들 것인지와 방식을 [../gx-design/HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 질문·선택으로 묻는다.
**영상·이미지 결과물의 선택지에는 Gemini 프롬프트 옵션을 반드시 포함한다.** before/after 비교 실물이 필요하면 after 실물 제작에 같은 경로를 적용한다.
polish 경로로 코드·파일을 이미 수정했으면 결과물이 이미 실물이므로 이 게이트는 "생략 보고"로 처리하고, 별도 매체의 실물이 필요한 경우에만 묻는다.

**핵심 모드**: 경량화하지 않는다 — 전체 모드와 동일하게 수행한다.

완료 기준: 실물 제작 여부를 물었고(결과물이 문서 자체이거나 polish로 이미 실물을 수정했으면 생략 보고), 선택된 경로의 산출물이 outputs/final/에 저장되었다.

## 위임 규칙 / 단계 보고

gx-design 스킬과 동일하다: 위임 시 11항목(프로젝트명/배경/목표/타깃/결과물 유형/필수 요구/제약/참고자료 경로/이전 단계 결과물 경로/저장 경로/완료 기준) 명시, 단계마다 4줄 보고(완료한 작업/생성한 파일/핵심 결정/다음 단계). 보고 첫머리에 현재 모드([전체]/[핵심], 승격했으면 `[승격] 단계명`)를 표기한다.
5번째 줄로 **실행량**을 붙인다: `위임 N회 · 외부 열람 N건 · 렌더 N장 · 토큰 N(호스트가 제공할 때만, 아니면 미측정)`. 추정치를 측정치처럼 쓰지 않는다. 최종 보고 때 단계별 합계 표를 `outputs/final/YYYY-MM-DD_<project>_run-log.md`로 저장한다([RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)의 비용 기록).

## Red Flags — 발견 즉시 해당 단계로 복귀

- 진단 없이 개선 방향·스타일 안을 제안하고 있다
- "요즘 느낌" 같은 모호어를 레퍼런스 취향 질문으로만 처리하고 개선 계기·목표·성공 기준을 묻지 않았다
- 유지 자산 목록을 확정하지 않고 제작에 들어갔다
- before/after 매핑 없이 새 디자인만 제시하고 있다
- 검수 통과 후 실물 제작 여부를 묻지 않고 명세 문서만 남긴 채 종료했다
- 점검 전용인데 이어가기 게이트 전에 파일을 수정했다
- 참조 파일을 읽지 못했는데 추측으로 그 단계를 진행하고 있다

| 합리화 | 실제 |
|---|---|
| "기존 파일을 읽었으니 파악은 끝났다" | 읽기는 인벤토리다. 진단이 아니다 — 문제 목록과 근거가 나와야 파악이다. |
| "사용자가 낡았다니까 스타일을 바꾸면 된다" | 낡음의 정체(비주얼? 패턴? 정보구조?)는 진단이 판정한다. 인상은 입력이지 결론이 아니다. |
| "레퍼런스만 정하면 방향이 나온다" | 레퍼런스는 하류 결정이다. 개선 목표와 성공 기준이 정해지기 전의 레퍼런스 선택은 근거가 없다. |
| "핵심 모드니까 게이트도 줄이자" | 핵심 모드가 줄이는 것은 내부 작업량이다. 게이트는 모드와 무관하게 유지된다. |
| "점검만이니 브리프는 생략하자" | 점검 전용은 브리프를 경량화할 뿐이다. 점검 대상·화면·기기 승인 없이 진단하면 범위가 흔들린다. |
| "지침을 못 읽었으니 일단 시안부터" | 읽기 실패는 게이트를 여는 사유가 아니다. 실패 파일·원인을 보고하고 멈추거나 질문 전용 인터뷰만 계속한다([HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#참조-파일-읽기-실패)). |
