# GX Redesign — 기존 디자인 개선·점검

기존 디자인의 개선과 품질 검토를 총괄한다. 요청에 맞춰 점검·부분 수정·리디자인을 진행한다. 점검 전용은 단계 0·1 뒤 보고로 완료하고, 방향·범위가 정해진 부분 수정은 아래 전용 경로를 따른다.
(처음부터 새로 만드는 요청이면 이 스킬이 아니라 gx-design 스킬을 로드한다.)
각 단계는 완료 기준을 충족했을 때만 통과한다.
실행 전 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md)의 공통 계약을 확인한다. 변경되지 않은 세션에서는 한 번 읽은 내용을 재사용한다.

## 시작 분기와 읽기 지도

먼저 요청·대상과 필요한 의존 자료만 확인한다. 명확한 점검·부분 수정에 전체 인벤토리·새 브리프·시장 조사·전략 후보를 선행하지 않는다.

- 명확한 점검은 대상·관련 상태를 확인하고 단계 1 진단 → 보고로 간다. 경량 범위 기록은 진단 보고에 포함한다. REDESIGN-INTERVIEW는 로드하지 않는다.
- 명확한 부분 다듬기는 해당 부분과 필요한 의존 자료만 읽고 관련 진단 → 단계 4 수정 → 단계 5 검수로 간다. 범위 기록·변경 ID는 기존 산출물에 남긴다.
- 인터뷰는 미확정 핵심 의도가 있을 때만 REDESIGN-INTERVIEW.md를 읽는다. 열린 필수 결정은 답변까지 기다리며, 작은 빈칸 때문에 새 프로젝트 전체 인터뷰를 시작하지 않는다.
- 전략은 방향이 열려 있을 때만 DESIGN-IT-TWICE.md와 design-strategy를 읽는다. 경쟁·트렌드 목표의 미검증 질문이 있을 때만 design-research를 읽는다.
- 진단·검수는 REVIEW-AXES와 creative-review, 수정은 creative-production의 해당 계약을 읽고 그 작업·매체에 필요한 참조 절만 추가한다. 모션만 점검하면 MOTION의 해당 매체·판정 절을 읽으며, 정보 위계·AI 티·프롬프트 등 무관한 절을 일괄 로드하지 않는다. 최종 버전 증거·관련 상태·회귀 검증은 유지한다.

## 모드 결정

- 스킬 인자에 "핵심"·"빠르게"·"경량"이 있으면 **핵심 모드**, "전체"·"풀"이 있으면 **전체 모드**로 시작한다.
- 명시가 없으면 기본은 핵심 모드다. 요청 범위·복잡도에서 실제 승격 신호가 확인되면 해당 단계만 전체 수준으로 올린다. 품질·범위·시간의 실제 교환이 있을 때만 사용자 결과 중심으로 선택을 묻는다. 내부 모드 질문으로 시작을 막지 않는다.
- **범위(진행 모드와 별개)**: "점검만"·"고치지 말고"·"테스트만"처럼 수정 금지가 분명하면 점검 전용이다. "점검하고 수정까지"는 수정 요청으로 처리한다. 특정 폼의 오류 안내처럼 대상·보존 조건이 확정된 개선은 부분 다듬기, 전체 재설계는 리디자인이다. 문맥상 수정 허용 범위가 모호할 때만 그 범위를 독립 질문으로 확인한다.
- 결정된 모드·범위와 근거를 개선 브리프·실행 기록에 남긴다.
- 전체 모드는 요청에 적용되는 단계의 전체 깊이를, 핵심 모드는 해당 단계의 **핵심 모드** 조항을 따른다. 모드 때문에 명확한 점검·부분 수정에 불필요한 인터뷰·조사·전략 단계를 추가하지 않는다.
- **미확정 필수 결정의 게이트는 모드와 무관하게 유지된다.** 기존 요청·답변의 승인 재사용을 먼저 적용하며 핵심 모드는 내부 작업량을 줄인다.
- 사용자가 도중에 전환을 요구하면 전환한다 — 이미 통과한 게이트는 다시 열지 않고, 남은 단계만 새 모드 규칙을 적용한다.
- 진행 모드는 **시작 깊이**다. 작업량 수치(리서치 축·외부 출처 상한, 제작 분량, 검수 독립성)와 단계별 승격 신호는 [RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)를 따른다 — 승격 신호가 생기면 그 단계만 전체 수준으로 올리고 사용자에게 한 줄로 고지한다(통과한 게이트는 유지).
- 규칙 문서(VISUAL-CRAFT·VISUAL-QUALITY·MOTION·UI-QUALITY·ANTI-TELL-CHECKLIST·PROMPT-PLAYBOOK)는 각 문서의 읽기 지도에 따라 필요한 절만 읽는다. 위임할 때는 문서 경로와 **읽을 절**을 함께 전달하고, 위임할 수 없으면 주 에이전트가 같은 지도로 읽는다. 진단·검수 역할은 자기 축이 판정하는 절을 전부 읽는다.

## 단계 0 — 자산 인벤토리 + 개선 브리프 (게이트)

미확정 핵심 의도가 있을 때만 [REDESIGN-INTERVIEW.md](REDESIGN-INTERVIEW.md)를 읽는다. 명확한 점검·부분 수정은 위 직접 경로를 먼저 적용하며 새 인터뷰·브리프 파일을 강제하지 않는다.

**개선의 필수 의도가 미확정이면 그 결정에 의존하는 개선안·스타일·코드·파일 변경·위임은 중단한다.** 인벤토리와 중립적 사실 확인은 가능하다. 요청·기존 답변으로 확정된 결정은 근거·범위 버전을 기록하고 재질문하지 않는다(HOST-COMPAT의 승인 재사용).

**핵심 모드**: 자산 인벤토리와 인터뷰는 전체 모드와 같다 — frontier가 빌 때까지 라운드를 반복하고, 첫 라운드 슬롯 순서는 [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#질문-슬롯-산정표)의 질문 슬롯 산정표(리디자인 행)를 따른다. 인벤토리로 확인된 대상·기기는 묻지 않는다. 나머지는 [../gx-design/BRIEF-INTERVIEW.md](../gx-design/BRIEF-INTERVIEW.md)의 핵심 모드 조항 준용.

**점검 전용**: 요청 대상 안의 자산 인벤토리를 수행한다. 점검 대상·화면/URL·기기와 해당 시 핵심 여정이 요청 또는 인벤토리로 확정되면 재승인 없이 진단 보고 머리에 `[요청에서 확정]`으로 표시하고 읽기 전용 진단을 수행한다. 필수 슬롯만 미정이면 그것만 묻고 답을 기다린다. 대상 원본은 수정하지 않는다. 범위가 열린 일반 리디자인에는 브리프 승인 게이트를 유지한다.

**참조 파일을 읽지 못하면**: [HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#참조-파일-읽기-실패)의 참조 파일 읽기 실패 절을 따른다 — 추측으로 대신하지 않고 실패 파일·원인을 보고한 뒤 멈추거나, 최소 규칙(인벤토리 사실 수집 + 개선 계기·목표·대상 범위·유지 자산만 묻는 질문 전용 인터뷰 → 개선 브리프 초안 승인)으로만 계속한다. 이때도 승인 전에는 개선안·스타일·무드·팔레트·레이아웃·콘셉트를 내놓지 않는다.

완료 기준: 적용 범위의 인벤토리와 필수 결정·근거·범위 버전이 개선 브리프에 기록되었다. 열린 방향의 리디자인에는 브리프 승인을 받았으며, 점검 전용·확정된 부분 수정은 요청·기존 답변을 재사용했다.

## 특정 지적·부분 다듬기

대상·보존 조건·원하는 결과가 확정된 요청은 해당 자료를 읽고 관련 문제를 진단한 뒤 단계 4 제작 → 단계 5 검수로 간다. 요청 자체와 기존 결정의 적용 범위를 기록하고 브리프·실물 제작 여부를 재질문하지 않는다. 새로운 브랜드·전체 리서치·전략 3안을 강제하지 않는다. 대상이 여러 개이거나 변경 허용 범위가 미정일 때만 그 결정부터 묻고 의존 제작·위임을 기다린다.

수정 뒤 관련 상태·폭·핵심 여정과 회귀를 같은 조건으로 확인한다. D/G/S/J/CH ID와 A/B/C 책임은 유지하고, 기존 ID가 없으면 해당 진단·목표·변경 ID를 기록한다. 새 방향·범위·보존 조건 변경이 필요하면 영향받는 결정만 다시 연다. 요청한 부분의 수정·검증·한계 보고로 완료한다.

## 단계 1 — 진단 (Audit)

정보 위계·과업·묶음이 점검 범위인 UI·웹·정보 그래픽은 [DESIGN-JUDGMENT.md](../gx-design/DESIGN-JUDGMENT.md)의 해당 절을 진단 입력에 포함한다. 실제 발견한 문제만 관찰하고 과업에 미칠 영향은 확인·추정·미검증으로 구분한다. 기존 진단 ID와 UI-QUALITY의 해당 이슈 형식을 유지하며 변경 방향과 확인 방법을 연결한다.

기존 디자인에 [../gx-design/REVIEW-AXES.md](../gx-design/REVIEW-AXES.md)의 2축 독립 검수를 적용한다.
단, 진단에서는 축 A의 입력을 조정한다 — 이전 브리프·전략 문서가 있으면 그것과의 일치를, 없으면 개선 브리프에 기록된 현행 목표 대비 적합성을 검수한다.
"낡았다"는 인상을 구체적 문제 목록(Critical/Major/Minor + 근거)으로 번역하는 단계다.
UX/UI 진단에는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §2를 적용해 시각·UX 비평과 구현 점검을 구분한다. 실제 화면·코드·조작 증거와 확인/추정/미검증을 기록하고, 진단 단계에서 임의로 수정하지 않는다.
모션이 있는 자산(또는 점검 대상에 모션이 있으면) [MOTION.md](../gx-design/MOTION.md)를 추가 입력으로 읽는다 — UI는 §A, 영상·모션 그래픽은 §B. 모션 지적은 MOTION §C 표(`요소·위치 | Before(전) | After(후) | Why(이유)`)로 기록하고, Why에는 A1~A8/B1~B8 규칙 ID와 관찰법을 적는다. 심각도는 진단표와 같은 체계를 쓴다.
최초 관찰은 요청 범위의 대표 상태 1개와 필수 조건으로 시작한다. 명시한 기기·핵심 여정·수용 조건은 실제로 확인하고, 관련 오류·긴 텍스트·모바일 배치·키보드·모션 위험이 있을 때만 해당 상태·폭·입력 방식을 더한다. 모든 작은 점검에 모바일·데스크톱 전체 여정을 추가하지 않는다. 실행 여정이 범위에 있으면 [VISUAL-QUALITY.md](../gx-design/VISUAL-QUALITY.md)의 해당 시나리오를 수행하고 증거 로그를 남긴다. 브라우저 도구가 없으면 폴백·시도·미검증을 `검증 한계`에 기록한다.

시각 구조·AI 티가 점검 범위인 UI·웹 화면은 [ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md)의 해당 절을 읽는다. 진단표에는 **실제로 발견된 항목만** 기록하고 `해당 없음` 목록은 출력하지 않는다. 각 행은 `문제 | 화면·위치 | 관찰 증거 | 왜 어색한지 | 무엇으로 바꿀지 | 심각도`를 포함하고 제작·검수에서 참조할 진단 ID(예: D-01)를 붙인다. 관찰되지 않은 문제는 추정으로 채우지 않고 `검증 한계`에 기록한다. 정상 카드·배경·아이콘은 화면 목적과 콘텐츠 구조로 판단한다.

**핵심 모드**: 축 A→축 B를 순차 진단한다(보고는 축별 분리 유지). 위임할 수 없으면 주 에이전트가 [creative-review 스킬](../creative-review/SKILL.md)을 읽고 각 축을 기록한다. 진단은 아직 제작 맥락이 없으므로 독립성 제약은 단계 5 검수에서 적용한다.

진단 보고 전 REVIEW-AXES의 해당 축과 creative-review의 검수 기준을 실제로 읽었는지 확인한다. DESIGN-JUDGMENT만 읽은 것으로 이 검수를 대신하지 않는다. 보고는 **축 A — 목표 적합성**, **축 B — 완성도**를 각각 제목이 있는 절로 나누며, 짧게 요청받아도 축을 하나의 목록으로 합치지 않는다. 참조를 읽지 못했으면 HOST-COMPAT의 읽기 실패 규칙에 따라 처리한다.

완료 기준: outputs/research/에 발견 항목만 담은 진단표와 검증 한계가 저장되었고, 각 진단 행에 관찰 증거·왜 어색한지·무엇으로 바꿀지가 있으며, 사용자에게 진단 요약을 보고했다. 점검 전용은 이 보고로 완료한다.

## 점검 전용 범위 — 보고로 완료

단계 0(확정 경량 브리프) → 단계 1(읽기 전용 진단) → 보고로 완료한다. 보고는 진단표·해당 시 모션 §C 표·실행 검증 로그·검증 한계를 포함한다. 필수 종료 질문이나 3지선다 도구를 띄우지 않고 가능한 후속 행동을 짧게 안내한다. 수정은 새로운 명시 요청이 있을 때 시작한다. 처음부터 "점검하고 수정까지" 요청했다면 승인된 수정 범위를 재사용하며, 미정인 범위만 확인한다.

후속 리디자인 요청은 기존 진단을 재사용하고 개선 브리프의 미정 항목만 보충한다. 경쟁·트렌드 목표가 있으면 단계 2, 큰 방향이 열려 있으면 단계 3을 적용한다. 정해진 진단 항목 수정은 아래 polish 경로로 합류한다. 단순 후속 안내나 무응답은 수정 승인이 아니다.

**polish 경로 계약** — 경량 개선 브리프에는 유지 자산·전략이 없으므로, polish로 합류하면 단계 4~6의 입력을 아래로 갈음한다.

- **수정 범위**: 사용자에게 보인 진단 ID 집합과 보존 범위에 대한 명시 응답을 기록한다. 예: `D-01·D-03 수정, 나머지 유지`. 사용자가 `D-02만`이라고 하면 그 ID만 적용한다. ID를 적지 않았다고 Critical·Major 전체로 조용히 확대하지 않는다. "지적 항목만 수정"의 집합이 모호하면 실제 ID 집합을 보여 주고 확인하며, 그 집합을 이미 보여 준 선택지에 응답했으면 재질문하지 않는다.
- **유지 자산**: 지적 항목 외 전부. 경량 브리프에 유지 자산이 없으므로 이 규칙으로 갈음한다 — 수정 범위 밖의 요소는 바꾸지 않는다.
- **선택 기록**: 기존 결과 로그에 `최소 개입 — 요청·답변으로 확정 · 수정 범위 = 진단 ID 목록 · 나머지 유지`와 근거·범위 버전을 덧붙인다. 부분 polish에 별도 전략 파일을 만들지 않는다.
- **단계 4 제작 입력**: 선택된 진단표 행의 `화면·위치 | 관찰 증거 | 무엇으로 바꿀지`. 변경 기록은 일반 리디자인과 같은 4열(`변경 ID → before → after → 근거`)로 남기고, 근거에는 선택된 진단 ID를 적는다.
- **단계 5 검수**: 축 C는 선택된 진단 ID의 해소와 회귀만 본다.
- **단계 6 실물 제작**: 코드·파일 수정이 결과물이면 그 최종 버전을 검수하고 완료한다. 이미 요청한 별도 매체 결과물은 재질문 없이 만들며, 미정인 추가 결과물이 필요할 때만 확인한다.

완료 기준: 확정된 경량 브리프 근거와 진단·한계를 저장하고 보고했다. 새 수정 요청이 있으면 그 범위·응답을 기록하고 해당 경로의 완료 기준을 따른다.

## 단계 2 — 갭 리서치 (조건부)

브리프의 개선 목표가 경쟁·트렌드와 관련되면 [design-research 스킬](../design-research/SKILL.md)의 역할과 산출물 계약에 따라 현행 대비 갭을 조사한다. 열린·미검증 질문이 남은 축만 실행하고 외부 출처 상한을 지킨다([RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)). 위임이 허용되고 서브에이전트 도구가 있으면 조사 역할에 브리프와 입력 11항목을 전달한다. 위임할 수 없으면 주 에이전트가 design-research를 읽고 갭을 조사한다.
관련 없으면 이 단계를 생략하고 생략 사실을 보고한다.

**핵심 모드**: 기본 생략한다. 브리프가 경쟁·트렌드 목표를 명시한 경우에만 조사 역할 1개 또는 주 에이전트가 경량 실행(상한 100줄)한다.

완료 기준: (실행 시) outputs/research/에 갭 리포트가 저장되었다.

## 단계 3 — 개선 전략

UI·웹 화면과 정보 전달 중심 그래픽의 개선안은 DESIGN-JUDGMENT의 판단을 근거로 삼고, 진단 문제 또는 승인된 브리프 목표에 직접 연결되는 변경 범위와 유지 조건을 명시한다.

방향이 열려 있을 때만 [design-strategy 스킬](../design-strategy/SKILL.md)과 [DESIGN-IT-TWICE.md](../gx-design/DESIGN-IT-TWICE.md)를 읽는다. 핵심 모드는 추천 스케치 1안과 필요할 때 실질적으로 다른 비교 1안, 전체 모드·명시적 3안 요청은 아래 강도 철학의 스케치 3안을 사용한다. 진단 ID와 대표 영역·핵심 상태로 비교하고 선택된 1안만 확장한다. 확정 강도·방향은 기존 선택을 재사용하며, 선택 전 통합·전체 확장·의존 위임은 하지 않는다:

- **A안 — 최소 개입**: 진단된 문제만 정밀 수정, 유지 자산 최대 보존
- **B안 — 리프레시**: 디자인 시스템 정비 + 문제 영역 우선 갱신
- **C안 — 리뉴얼**: 불가침 자산만 남기고 전면 재설계

각 후보는 해결할 진단 ID·해결 범위·리스크·작업량을 명시한다. 비교 후보가 있으면 장식 차이가 아닌 개입 범위·과업 해결 차이를 검토한다. 유지 자산·톤 기준으로 공유되는 형태는 억지로 바꾸지 않는다. 근거 있는 추천과 함께 HOST-COMPAT에 따라 선택받는다.
**변경 범위 잠금**: 모든 개선 후보는 진단 문제 또는 승인된 개선 브리프 목표에 연결된 변경만 제안한다. 단순 인상이나 검색 후보를 근거로 진단되지 않은 영역까지 재설계하지 않는다.
개선 브리프에 디자인 톤 기준이 있으면 명시된 강도를 적용한다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4). hard의 팔레트·타이포·톤·형태는 제약이며 이탈은 근거와 승인이 필요하다. soft는 출발점이며 이탈 근거를 기록한다.
UI·그래픽 개선안의 톤 다이얼과 근거는 내부 기록에 남기고 사용자에게는 과업·읽힘·정보량·움직임의 차이를 설명한다. 모션 범위가 결과를 바꾸는 미확정 결정일 때만 별도 문항으로 묻는다([DESIGN-IT-TWICE.md](../gx-design/DESIGN-IT-TWICE.md)의 모션 범위 절차, [MOTION.md](../gx-design/MOTION.md)). 현행 자산의 다이얼을 진단에서 읽었으면 최소 개입 후보는 그 값에 가깝게 둔다.
UX/UI 전략에는 브리프의 화면 목적·핵심 과업과 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §1을 전달한다. 새 디자인 후보가 필요하면 [DESIGN-INTELLIGENCE.md](../gx-design/DESIGN-INTELLIGENCE.md)의 검증된 검색 결과를 참고한다. 검색으로 유지 자산이나 개선 범위를 바꾸지 않는다.

**핵심 모드**: 방향 비교가 필요한 경우 한 주체가 추천 스케치 1안과 필요할 때 실질적으로 다른 비교 1안을 작성한다. 추천은 목표·개선 강도 허용치에 근거하고 미확정 선택만 질문하며 확정된 1안만 확장한다. 기존 방향은 재사용한다. 후보 거절 처리와 필요한 단계 승격은 RUN-BUDGET을 따른다.

완료 기준: 적용 경로의 후보·선택·확장 또는 기존 방향 재사용 근거·범위 버전이 기록됐다. 후보 수는 DESIGN-IT-TWICE의 핵심/전체 조건을 따른다.

## 단계 4 — 제작

제작은 [creative-production 스킬](../creative-production/SKILL.md)의 해당 계약을 따른다. 단순 부분 수정은 오케스트레이터가 시작한다. 실제 규모·위험·역할 분리의 실익이 있고 위임 권한·도구가 있을 때만 입력 11항목·선택 기록·관련 진단·보존 조건·참조 절을 전달한다. 위임할 수 없으면 주 에이전트가 같은 계약으로 제작한다.
polish로 합류했으면 "선택된 전략·유지 자산" 입력은 위 polish 경로 계약(명시된 수정 ID 집합, 나머지 보존, 기존 결과 로그의 선택 기록)으로 충족된다.

**모든 변경 항목은 변경 ID → before → after → 근거의 4열로 기록하고(변경 ID 예: CH-01), 근거에는 `진단 ID 또는 승인된 개선 브리프 목표(기준 ID)`를 적는다(polish 경로는 진단 ID).** 둘 중 어느 것에도 연결되지 않는 변경은 제작 범위에서 제외한다. 검수 축 C는 이 변경 ID로 `변경 ID → 진단/목표 ID → 검수 결과`를 추적한다.
유지 자산으로 지정된 요소는 변경하지 않는다.
디자인 톤 기준이 있으면 원본 경로·명시된 강도·승인된 이탈을 전달하고 hard 토큰은 그대로 적용하며 soft 이탈 근거는 기록한다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4).
UI·그래픽·UX/UI 산출물은 [../gx-design/VISUAL-CRAFT.md](../gx-design/VISUAL-CRAFT.md) 경로도 위임 프롬프트에 포함한다(안티-슬롭·톤 다이얼·일관성·모션).
UI·그래픽·UX/UI·Gemini 웹 생성 산출물은 [../gx-design/ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md) 경로도 함께 포함한다(요소·카피·구조 텔 자체 점검 — 완료 전 1회).
UI·웹 화면과 정보 전달 중심 그래픽은 DESIGN-JUDGMENT.md도 제작 입력에 포함한다. 기존 변경 ID·진단/목표 ID의 추적을 유지하고, 변경 후 같은 콘텐츠·뷰포트·상태에서 원래 결함과 새 문제를 재확인한다. 위임할 수 없으면 주 에이전트가 읽는다.
모션이 있는 산출물은 [MOTION.md](../gx-design/MOTION.md) 경로와 선택 기록의 다이얼·모션 범위를 함께 전달한다(UI = §A, 영상·모션 그래픽 = §B). 모션 변경도 before → after → 근거로 기록한다.
UX/UI 제작에는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md)를 전달해 관련 문구·예외 상태를 반영한다. 구현 지침 검색이 필요하면 [DESIGN-INTELLIGENCE.md](../gx-design/DESIGN-INTELLIGENCE.md)도 전달하며, 위임할 수 없으면 주 에이전트가 읽는다.
레퍼런스 이미지·영상을 아트디렉션 입력으로 쓰는 제작이면 [../gx-design/REFERENCE-DRIVEN.md](../gx-design/REFERENCE-DRIVEN.md) 경로도 위임 프롬프트에 포함한다(근접도 다이얼·visual DNA·저작권 가드레일 — 타인 자산 재현 금지).
제품 소개 화면·커서 데모·촬영 장면이 요청된 영역은 [PRODUCT-SCENES.md](../gx-design/PRODUCT-SCENES.md)를 읽고 실제 동작 UI와 연출을 구분한다. 진단·회귀에서 구조·반복 후보 관찰이 필요할 때만 [references/OBSERVATION.md](../gx-design/references/OBSERVATION.md)의 선택 도구를 사용한다. BX·그래픽·영상·Gemini·.pen·문서 경로는 유지한다.

규칙 문서를 전달할 때는 경로와 함께 각 문서의 읽기 지도에서 고른 **읽을 절**을 적는다(예: MOTION — UI는 §0·§A·§C, 영상은 §0·§B·§C). 위임할 수 없으면 주 에이전트가 같은 절을 읽는다.

**핵심 모드**: 위임 프롬프트에 매체별 필수 섹션과 화면(씬)당 분량 상한(공통 섹션 60줄 · 화면당 40줄 · 씬당 15줄 — [RUN-BUDGET.md](../gx-design/RUN-BUDGET.md)의 제작 분량)을 명시한다. 총량 상한은 두지 않는다 — 다화면 개선을 자르지 않는다. before/after 매핑 의무는 모드와 무관하게 유지된다.

완료 기준: 요청 위치의 산출물과 before/after·근거 매핑이 있다(위치 미정이면 outputs/production/). 단순 수정은 원래 파일과 간결한 변경·증거 로그로 충족하며 별도 명세 사본을 만들지 않는다.

## 단계 5 — 검수

[REVIEW-AXES.md](../gx-design/REVIEW-AXES.md)의 2축에 축 C를 추가하며 관련 A/B/C 판정은 별도로 유지한다. 단순 작업은 오케스트레이터가 creative-review의 해당 절을 읽고 축 A→B→C를 순서대로 각각 기록한다. 작업 위험·규모가 별도 검토를 정당화하고 위임 권한·도구가 있으면 최종 축 B만 다른 맥락 1개에 맡긴다. 자동 축별 팬아웃을 하지 않으며 위임할 수 없으면 주 에이전트가 같은 필수 기준으로 점검한다:

- **축 C — 개선 목표 달성**: 승인된 범위의 진단 Critical/Major가 해소되었는가, 유지 자산이 보존되었는가, 브리프 성공 기준 표(기준 ID·기준선)를 같은 관찰법으로 재측정해 목표값에 도달했는가 — 절차는 [creative-review 스킬](../creative-review/SKILL.md)의 개선 목표 달성(리디자인 축 C) 절.
- 축 C는 개선 브리프 성공 기준 표(기준 ID·기준선)의 같은 관찰법으로 재측정해 결과 열을 채운다 — 상세는 [creative-review 스킬](../creative-review/SKILL.md).

축 C는 제작 과정에서 진단되지 않은 새 안티패턴이 생기지 않았는지도 회귀 검사한다. 모든 변경이 진단 문제 또는 승인된 개선 브리프 목표를 해결하는지 다시 확인하고, 근거 없는 변경이나 새 결함이 발견되면 제작 단계로 되돌린다. 발견 근거와 심각도는 [UI-QUALITY.md](../gx-design/UI-QUALITY.md) §2의 기준으로 기록한다.

디자인 톤 기준이 있으면 축 A에 톤 준수 점검을 포함한다([../gx-design/DESIGN-TONE-ANCHOR.md](../gx-design/DESIGN-TONE-ANCHOR.md) §4).
레퍼런스 입력을 쓴 제작이면 축 A 검수에 [../gx-design/REFERENCE-DRIVEN.md](../gx-design/REFERENCE-DRIVEN.md) 경로를 전달하고 근접도·저작권 가드 점검을 포함한다(REFERENCE-DRIVEN §6).
UI·그래픽·코드 렌더·Gemini 웹 생성 산출물이면 축 B 검수에 [../gx-design/ANTI-TELL-CHECKLIST.md](../gx-design/ANTI-TELL-CHECKLIST.md) 경로를 전달한다(요소·카피 텔 점검).
UI·웹 화면과 정보 전달 중심 그래픽이면 축 B에 DESIGN-JUDGMENT.md도 포함해 시선·묶음·읽힘을 확인한다. 축 C는 기존 진단·목표·변경 ID로 문제 해소, 유지 조건 보존과 관련 상태·뷰포트의 회귀를 대조한다.
모션이 있는 산출물이면 축 B 검수에 [MOTION.md](../gx-design/MOTION.md) 경로를 전달하고 모션 지적은 §C 표로 받는다.
UX/UI이면 축 B에 [UI-QUALITY.md](../gx-design/UI-QUALITY.md), 화면별 목적·핵심 과업, 핵심 여정, 검색 채택 기록(있을 때)을 전달한다. 축 C는 해당 진단 이슈의 해소를 같은 증거 기준으로 확인한다.
polish 경로면 축 C는 선택된 진단 ID의 해소와 회귀만 본다(브리프 성공 기준·유지 자산 목록 대신 polish 경로 계약을 기준으로 삼는다).

**핵심 모드**: REVIEW-AXES와 RUN-BUDGET의 위험·규모 조건이 별도 검토를 정당화할 때만 위임 가능한 최종 축 B를 다른 실행 맥락 1개에 맡긴다. 단순 audit·polish는 오케스트레이터 1개로 관련 A/B/C를 나눠 기록한다. 별도 맥락이 실제 수행하지 않았으면 축 B 실물을 다시 관찰하고 원시 로그와 대조해 `재열람 기반 자체 검수(동일 맥락 검수)`로 표시한다. 필수 판정·영향 재검수·최종 증거 기준은 유지한다.

완료 기준: 세 축이 REVIEW-AXES의 최종 버전·필수 증거·범위 내 Critical/Major 조건을 충족하고, 해당 상태의 산출물이 요청 위치에 저장되었으며(미정이면 outputs/final/), 사용자에게 결과·예외·미검증 한계를 보고했다.

## 단계 6 — 요청 결과물 완성

기존 수정·검수 뒤 별도 실물 경로가 필요한 경우 [PRODUCTION-HANDOFF.md](../gx-design/PRODUCTION-HANDOFF.md)를 읽는다. 코드·파일이 요청 결과물이고 이미 최종 검수됐다면 이 단계를 다시 열지 않는다.
결과물·방식이 요청이나 답변에서 확정됐으면 승인 재사용으로 해당 실물을 완성한다. 미정인 경로만 HOST-COMPAT에 따라 묻는다. 영상·이미지의 경로 선택이 필요하면 Gemini 프롬프트 옵션도 포함한다. before/after 비교 실물에도 같은 계약을 적용한다.
코드·파일 수정이 결과물이면 최종 수정본을 검수하고 완료한다. 문서·프롬프트만 요청했으면 실물을 자동 추가하지 않는다. 추가 실물을 만든 뒤 최종 버전의 검수와 변경 영향 재검수는 PRODUCTION-HANDOFF·REVIEW-AXES를 따른다.

**핵심 모드**: 경량화하지 않는다 — 전체 모드와 동일하게 수행한다.

완료 기준: 요청한 경로·위치의 결과물이 저장되고(위치 미정이면 outputs/final/) 최종 버전의 검수 상태·한계를 보고했다. 프롬프트·명세 완성과 PNG·MP4 완성은 서로 구분한다.

## 위임 규칙 / 단계 보고

위임 시 입력 11항목(프로젝트명/배경/목표/타깃/결과물 유형/필수 요구/제약/참고자료 경로/이전 결과물 경로/저장 경로/완료 기준)을 전달한다. 단순 audit·polish는 단계별 보고·새 템플릿 파일을 강제하지 않고 범위·버전·이슈/변경 ID·관찰 조건·판정·미검증·실행량을 한 개의 간결한 결과 로그에 남긴다. 원본 수정과 보고 저장은 구분한다.
다단계 전체 작업은 gx-design의 단계 보고 형식(완료 작업/파일/핵심 결정/다음 단계, 내부 모드·승격 기록과 실행량)을 따른다. 측정 불가한 값은 미측정으로 적고 RUN-BUDGET의 비용 기록을 적용한다.

## Red Flags — 발견 즉시 해당 단계로 복귀

- 진단 없이 개선 방향·스타일 안을 제안하고 있다
- "요즘 느낌" 같은 모호어를 레퍼런스 취향 질문으로만 처리하고 개선 계기·목표·성공 기준을 묻지 않았다
- 유지 자산 목록을 확정하지 않고 제작에 들어갔다
- before/after 매핑 없이 새 디자인만 제시하고 있다
- 실물 요청을 받고 명세만 남긴 채 실물 완료로 보고했다
- 점검 전용인데 새 수정 요청 없이 대상 파일을 수정했다
- 참조 파일을 읽지 못했는데 추측으로 그 단계를 진행하고 있다

| 합리화 | 실제 |
|---|---|
| "기존 파일을 읽었으니 파악은 끝났다" | 읽기는 인벤토리다. 진단이 아니다 — 문제 목록과 근거가 나와야 파악이다. |
| "사용자가 낡았다니까 스타일을 바꾸면 된다" | 낡음의 정체(비주얼? 패턴? 정보구조?)는 진단이 판정한다. 인상은 입력이지 결론이 아니다. |
| "레퍼런스만 정하면 방향이 나온다" | 레퍼런스는 하류 결정이다. 개선 목표와 성공 기준이 정해지기 전의 레퍼런스 선택은 근거가 없다. |
| "핵심 모드니까 게이트도 줄이자" | 미해결 필수 결정은 양 모드 모두 기다리고, 이미 받은 승인은 양 모드 모두 재사용한다. |
| "핵심 모드라서 질문을 줄이고 [가정]으로 채웠다" | 핵심 모드가 줄이는 것은 브리프 승인 뒤의 내부 작업량이다. 인터뷰는 frontier가 빌 때까지. |
| "점검만이니 브리프는 생략하자" | 요청·자료로 확정한 점검 대상·화면·기기·해당 여정은 기록하고 바로 진단한다. 열린 필수 정보만 묻고 점검 보고로 완료한다. |
| "지침을 못 읽었으니 일단 시안부터" | 읽기 실패는 게이트를 여는 사유가 아니다. 실패 파일·원인을 보고하고 멈추거나 질문 전용 인터뷰만 계속한다([HOST-COMPAT.md](../gx-design/HOST-COMPAT.md#참조-파일-읽기-실패)). |
