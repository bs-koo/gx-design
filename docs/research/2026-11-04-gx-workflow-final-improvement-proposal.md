# GX Design 워크플로우 최종 개선 제안

조사일: 2026-11-04. 기준: 로컬 gx-design 0.13.0. 범위: 사용자 대화·제작·검수·평가·외부 디자인 도구 연결. 상태: 구현 전 최종 제안.

**권장 방향은 기존 진입점과 과업·브랜드·증거 체계를 유지하면서, 사용자 결정의 대기·재사용 계약과 최종 실물 검수를 강화하는 것이다.** 중요한 의도는 충분히 묻고, 이미 정해진 것과 제작자가 판단할 사항은 반복해서 묻지 않는다. Stageshow 등 외부 도구는 작업별 제작·검증 수단으로 연결한다.

## 1. 검토 방법과 확인 범위

- 세 독립 검토가 사용자 질문·대기, 제작·검수 구조, 외부 스킬의 최신 계약을 각각 조사했다. 주 검토자는 평가 러너·테스트를 확인하고 중복·상충하는 제안을 조정했다.
- 기존 테스트를 `python -B -m unittest discover -s tests -v`로 실행해 **76개 통과**를 확인했다. 이는 문서 구조·문구 계약·호환성·평가 코드 단위 검사이며 실제 모델의 모든 대화 행동을 보장하지 않는다.
- 실제 모델을 호출하지 않는 평가 러너 모의 실험 세 건을 수행했다. 질문 없이 완료 응답을 반환해도 후속 승인 답변을 전송했고, 다른 결정의 질문에도 준비된 답변을 전송했다. 턴 안에서 생성 후 삭제된 파일은 전후 snapshot 차이에 나타나지 않았다.
- 외부 플러그인 설치·훅 실행·전체 모델 평가·제품 화면 제작은 수행하지 않았다. 따라서 실제 질문 대기 실패율, 결과 품질 향상률, 시간·토큰 절감률은 미측정이다.

이 문서의 우선순위는 개선 작업의 순서다. 문구 충돌이나 평가 사각지대를 실제 무단 제작 사고가 관찰된 것처럼 해석하지 않는다. 이전 [Stageshow 조사](2026-11-04-stageshow-design-quality.md)의 제안은 이 문서에서 보정했다.

## 2. 유지할 강점

현재 규격에는 상류 결정부터 질문하기, 프로젝트에서 아는 사실 재질문 금지, 추천과 근거 제시, 승인·선택 후 진행, 점검 전용의 수정 금지, polish의 진단 범위 잠금이 이미 있다. 질문 총량을 임의로 제한하지 않고 필요한 결정이 해소될 때까지 묻는 원칙도 보존할 가치가 있다.

브랜드 정본 우선, 과업·정보 관계 중심 판단, 검증된 관찰과 사용자 영향 추정의 구분, 정상·예외 상태·접근성·실행 여정 확인, A/B/C 검수 축과 D/G/S/J/CH ID도 유지한다. 외부 스킬 전체로 교체할 근거는 충분하지 않다.

## 4. 사용자 결정과 대기의 단일 계약

### 4.1 무엇을 물을 것인가

질문 총량을 고정하지 않는다. 목표·타깃·핵심 과업·범위·유지 자산·결과물처럼 결과를 바꾸는 미확정 결정은 필요한 만큼 확인한다. 핵심 모드라는 이유로 생략하지 않는다. 반대로 결정 트리에 넣을 수 있다는 이유만으로 모든 취향·세부 구현을 질문으로 만들지 않는다.

각 결정에는 **사용자 판단이 필요한가, 자료에서 확인 가능한가, 이미 답했는가, 위임받았는가, 이번 단계의 결과를 실제로 바꾸는가**를 확인한다. 작업을 막는 사용자 결정만 대기 대상으로 삼는다. 기준이 이미 정해진 자잘한 간격·구현 선택은 승인된 범위 안에서 제작자가 판단한다. 선택 취향을 사용자가 미정이라고 한 것과 판단을 맡긴 것은 구분한다.

| 결정 종류 | 처리 |
|---|---|
| 요청·파일에서 확인된 사실 | 확인한 내용을 짧게 알리고 질문 생략 |
| 목표·타깃·범위 등 미확정 의도 | 질문하고 관련 제작·전략 확정을 대기 |
| 사용자가 명시적으로 위임한 결정 | 위임 범위 안에서 선택하고 근거 기록 |
| 기존 기준 내 구현 세부 | 제작자가 결정. 승인·위임 범위를 벗어나는 의미·동작·브랜드 변경이 필요하면 사용자 결정으로 승격 |
| 선호가 없거나 아직 모르는 취향 | '지정 없음'과 '판단 맡김'을 구분. 무응답을 위임으로 취급하지 않음 |
| 요청에 없는 배포·외부 전송·추가 유료 실행 | 제작 승인으로 자동 확대하지 않음. 적용되는 실행 권한에 따름 |

### 4.2 결정 상태와 응답 적용

기존 브리프·선택 기록에 결정 ID, 현재 값, 상태, 근거 발화/자료, 적용 범위·버전, 영향 단계를 남긴다. 별도 문서 정본을 또 만들기보다 기존 기록을 확장한다. 상태는 미확정·제안됨·응답 대기·사용자 확정·위임됨·변경됨을 구분한다.

필수 응답을 요청하면 무엇을 기다리고 어떤 작업이 멈췄는지 표시한다. 해당 결정과 그에 의존하는 제작·파일 변경·위임은 중단한다. 미리 실행한 작업자의 결과가 답변 뒤에 도착하더라도 현재 결정 버전과 맞는지 확인하기 전에는 채택하지 않는다.

| 상황 | 해야 할 행동 |
|---|---|
| 비동기 질문 도구가 질문 등록만 반환 | 응답 대기 유지. 등록 성공을 답변으로 해석하지 않음 |
| 아무 답 없음·시간 경과·창 닫기·취소 | 승인·위임·추천안 채택으로 간주하지 않음 |
| 기본으로 선택돼 보이는 옵션 | 기본값을 명확히 제시하고 사용자가 확인·제출한 경우에만 응답. 질문 등록·자동 제출은 미응답 |
| 세 문항 중 하나만 답함 | 그 문항만 확정. 나머지 필수 문항과 관련 작업은 대기 |
| 자유 응답이 선택지와 다름 | 의미를 해석해 반영. 필수 결정이 모호할 때만 좁혀 질문 |
| '추천으로' 응답 | 지칭하는 현재 결정의 추천에 적용. 여러 추천 중 대상이 모호하면 확인 |
| '나머지는 네가 판단해' | 현재 설명된 작업 범위에 대한 위임으로 기록. 다른 업무·권한까지 확대하지 않음 |
| '그만, 진행해' | 현재 설명된 범위의 인터뷰 종료·디자인 판단 위임. 기존 금지·보존 조건 유지, 점검→수정·외부 게시 권한으로 확대 금지. 미해결 값과 근거 기록 |
| '그만'·'멈춰' | 작업 중단 의도로 우선 처리. 진행 위임으로 해석하지 않음 |
| 예전 질문에 늦은 답이 도착 | 결정 ID·범위 버전 대조. 이미 대체된 결정에 자동 반영하지 않음 |
| 대기 중 사용자가 다른 질문·상태 요청 | 짧게 답하고 원래 필수 결정은 대기 유지 |
| 질문 도구 사용 불가 | 대화 질문으로 전환. 답변 형식은 자유롭게 허용 |

허용되는 독립 작업은 사용자가 지정한 자료 읽기, 현행 자산 인벤토리, 중립적 사실 확인 등이다. 새 방향의 시안·카피·코드 생성, 전략 선택을 전제한 조사 확장, 원본 수정은 의존 작업이다. 단순히 '조사'라고 부르는 것으로 승인 전 작업을 정당화하지 않는다.

필수 대기 상태에서는 해당 호스트가 지원하는 대기·재개 방식을 사용한다. 긴 대기 중 모델·도구를 불필요하게 반복 호출하지 않는다. 선택적 선호 질문을 보낸 뒤 독립 작업을 수행할 수 있다. 충분한 응답 기회를 제공한 뒤에도 답이 없으면 사용자 선호는 '지정 없음'으로 기록하고, 승인된 목표·기준 안의 제작자 판단은 계속할 수 있다. 이는 필수 결정에는 적용하지 않으며, 무응답을 사용자 승인·위임으로 기록하지 않는다.

### 4.3 승인 재사용과 변경

사용자가 '모바일·데스크톱에서 작동하는 React 화면을 만들어줘'라고 결과물과 방식을 정했다면 뒷단에서 실물 제작 여부를 다시 묻지 않는다. 미정인 결정이 모두 해소되고 실행 의도도 분명하면 요청을 승인 근거로 기록한다. 큰 방향이 열린 신규 작업은 브리프·대표 방향 선택을 유지한다.

범위가 바뀌면 목표·타깃·유지 자산·산출물·게시 대상 중 무엇이 바뀌었는지 확인하고 영향받는 승인과 산출물만 갱신한다. 변경과 무관한 기존 답변은 유지한다. '전략을 바꿔줘'를 기존 브랜드 보존 해제나 배포 승인으로 확대하지 않는다.

## 5. 질문과 추천의 사용성

첫 안내에는 **이해한 목표·유지할 것·만들 결과물·남은 핵심 결정**만 짧게 보여준다. 내부 모드·frontier·다이얼 숫자·문서 이름을 사용자의 선택지로 먼저 내세우지 않는다. 사용자가 전체/핵심 모드를 지정하면 존중하고, 미지정일 때는 요청 범위에 맞는 내부 실행 깊이를 적용한다. 품질·범위·시간의 실제 교환이 있을 때만 사용자에게 선택을 묻는다.

질문은 결정 하나를 중심으로 쓴다. 한 문항에 '전체/핵심 × 점검/수정' 같은 서로 다른 판단을 숨겨 넣지 않는다. 관련 질문은 묶되 호스트 표시 한도를 질문 총량이나 이해도 지표로 사용하지 않는다. 이전 답으로 해소된 질문은 제거하고 남은 핵심 결정부터 묻는다.

| 요소 | 질문 작성 기준 |
|---|---|
| 요지 | 사용자가 무엇을 결정하는지 한 문장으로 표시 |
| 필요성 | 답에 따라 무엇이 달라지는지 설명. 내부 절차 준수 자체는 질문 이유가 아님 |
| 추천 | 사용자 목표·기존 자산·제약에 근거한 한 안. 근거가 없으면 억지 추천을 만들지 않음 |
| 대안 | 선택 후 결과와 비용·보존 범위의 차이를 설명. 모호한 '고급/기본' 비교 금지 |
| 형식 | 단일/복수 선택을 명확히 하고 자유 응답 허용. 사실 입력에는 억지 객관식 금지 |
| 강요 방지 | 추천 거절·다른 의견을 유효한 응답으로 처리. '모름'을 무조건 추천 수락으로 변환하지 않음 |
| 결과 | 무엇을 확정했고 무엇이 남았는지 짧게 확인 |

**제안 문구 예시 — 변경 범위가 열린 경우**

> 기존 색과 메뉴는 유지하는 것으로 이해했습니다. 정보 배치까지 바꿔도 되는지에 따라 수정 범위가 달라집니다.
>
> A. 기존 구조에서 가독성·강조만 조정 — 운영 방식을 보존하고 싶다면 추천합니다.
> B. 정보 배치와 탐색 순서도 재구성 — 더 큰 개선이 가능하지만 화면 구조가 달라집니다.
>
> 어느 범위까지 허용할까요? 다른 기준을 적어주셔도 됩니다. 답변 전에는 기존 화면과 자료만 확인하겠습니다.

이 예시의 추천은 '운영 방식 보존'이라는 조건에 따른 것이다. 실제 관찰이 없는데 구조 변경 효과를 단정하거나 사용자의 목표를 만들어내지 않는다.

**질문이 불필요한 예시**: '기존 디자인을 유지하고 신청 폼의 오류 안내만 고쳐줘'라면 대상 폼·오류 조건을 자료에서 확인한 뒤 관련 문구·상태를 수정한다. 신규 브랜드·스타일 3안·전체 리서치·실물 제작 여부를 다시 묻지 않는다. 대상 폼이 여러 개라면 어느 폼인지 먼저 확인한다.

## 6. 작업 의도별 워크플로우

| 요청 | 필요한 경로 | 멈출 지점 |
|---|---|---|
| 점검만·고치지 말고 | 대상·기기·해당 시 여정 확인 → 읽기 전용 진단 → 근거·한계 보고 | 수정하지 않고 완료. 후속 수정은 새 명시 요청이 있을 때 |
| 특정 지적·부분 다듬기 | 대상·보존 조건 확인 → 해당 부분 수정 → 관련 상태·폭·회귀 확인 | 새 방향·범위가 필요할 때만 질문 |
| 범위가 정해진 리디자인 | 현행 before → 진단·목표 → 필요한 변경 → 같은 조건 after → 검수 | 미확정 변경 강도·유지 조건이 있을 때 |
| 신규 UI·전체 리뉴얼 | 의도·브랜드·결과물 확정 → 필요한 조사 → 방향 탐색 → 대표 실물 → 확장 제작 → 검수 | 미확정 의도와 실제로 경쟁하는 방향 선택 |
| 후보 비교·탐색 요청 | 요청·자료로 비교 범위 확정(미정만 확인) → 판정 가능한 대표 후보 → 사용자 선택 → 선택안 통합 | 후보 선택 전 통합·전체 확장 금지 |
| 제품 소개 화면·데모 | 위치·크기·제품 메시지 → 예제 기반 스틸 → 모션 → 촬영·프레임 검수 | 미정인 표현 목표 또는 요청된 후보 선택 |
| 명세·브랜드 가이드·프롬프트만 | 해당 문서 제작 → 문서 수용 기준 검수 | 실물 제작을 자동으로 추가하지 않음 |

점검 종료 시에는 필수 3지선다 도구를 다시 띄우기보다, 요청된 점검을 완료하고 가능한 후속 행동을 짧게 안내하는 안을 권한다. '수정까지 이어서'가 이미 요청됐다면 점검 전용으로 잘못 분류하지 않는다. 수정 범위가 불분명할 때만 질문한다. 이는 현행 이어가기 게이트·README·테스트의 명시적 정책 변경이므로 함께 갱신해야 한다.

polish 선택지에는 'D-01·D-03 수정, 나머지 유지'처럼 실제 수정 집합을 명시한다. 사용자가 'D-02만'이라고 하면 D-02만 적용한다. 진단 ID를 적지 않았다는 이유로 Critical·Major 전체로 조용히 확대하지 않는다. 이미 수정 집합을 보여줬고 사용자가 그 선택지를 골랐다면 같은 범위를 다시 묻지 않는다.

전략 3안은 실질적으로 방향이 열려 있을 때 유지한다. 이미 방향이 정해진 작업에는 생략한다. 방향 비교는 팔레트만 바꾼 완성 화면 세 벌보다 대표 영역·핵심 상태로 판단 가능한 소규모 후보를 사용한다. 사용자에게 승인을 받기 위해 요청하지 않은 전체 후보 세 벌을 먼저 만들지 않는다.

UI/소개 장면 분기 외에 BX·그래픽·영상·Gemini·.pen·문서 경로도 보존한다. 이미지 생성 프롬프트의 완성과 실제 이미지 파일 완성, 영상 명세와 MP4 완성은 각각 다른 결과물 상태로 보고한다.

분류는 프로젝트 전체에 하나만 붙이지 않는다. 산출물·영역마다 **사용 목적 / 실제 동작인지 연출인지 / 파일·코드·문서 형식**을 구분한다. 예를 들어 랜딩의 CTA·문의 폼은 실제 UI이고 히어로 안의 커서 데모는 연출이다. 홍보 페이지라는 이유로 실제 버튼·폼의 검증을 면제하지 않는다.

## 7. 실물 품질과 최종 검수

**기존에도 제작 중 실물 검증은 있다.** 필요한 변경은 모든 실물 검증을 새로 도입하는 것이 아니라, 초기에 합의한 결과물 형식과 마지막 파일의 검수 상태를 일치시키는 것이다.

1. 결과물이 실물일 때는 대표 화면·컷을 먼저 만들어 큰 위계·밀도·브랜드 표현을 확인한다.
2. 대표 결과가 맞으면 기존 토큰·컴포넌트로 확장한다. 기준 예제는 출발 품질이며 시각적 복제 목표가 아니다.
3. 정상·오류·빈 상태·권한·긴 텍스트·실제 데이터 관계·관련 폭·입력 방식 등 해당 위험을 확인한다. 기존 UI-QUALITY와 VISUAL-QUALITY를 재사용한다.
4. 최종 결과의 버전 또는 해시·경로를 검수 근거에 기록하고 기존 실행 로그의 fixture·상태·뷰포트·환경을 함께 참조한다. 수정·재생성·내보내기로 결과가 바뀌면 영향받는 검수 결과는 다시 확인한다. 같은 빌드의 다른 상태까지 검수 완료로 확대하지 않는다.
5. A/B/C 축의 근거와 판정은 분리 유지한다. 사용자에게는 상위 문제·해결 여부·남은 결정 위주로 간단히 보고하고 상세 축별 기록을 연결한다.

UI의 클릭·입력은 실제 과업 실행으로, 소개 데모의 커서는 연출과 프레임으로 검증한다. 영상은 장면 시작·중간·끝과 핵심 모션·가독 구간·최종 출력 파일을 확인한다. 브랜드·그래픽은 실제 용도 크기의 결과와 해당 매체 수용 조건을 확인한다. 검증 불가·도구 오류·실제 제품 결함을 서로 구분한다.

### 7.1 통과 기준 보정

모든 Major를 전역 0건으로 만드는 규칙은 채택하지 않는다. 작업 시작 시 정한 범위·필수 수용 기준과 연결된 Critical·Major를 해결해야 해당 범위 통과다. 범위 밖 문제는 기록하고, 수정 중 새로 만든 회귀는 관련 범위로 포함한다. 취향 차이나 관찰하지 못한 가설을 결함으로 승격하지 않는다.

범위 내 Major가 남아 있으면 '수정 필요'로 보고한다. 사용자가 해당 결함을 명시적으로 수용하면 '예외 수용'으로 남기며, 결함이 해결된 통과로 바꾸지 않는다. 검증하지 못했으면 '미검증'으로 남긴다. 필수 수용 조건이 미검증이면 해당 범위의 통과를 보류하고, 범위 밖 미검증은 한계로 보고한다. 정성 목표가 사용자 판단에 달렸으면 기술 검수 상태와 취향 확인 대기를 구분한다.

### 7.2 반복 예산과 검수 무효화

초기 제안은 제작자 polish와 검수 후 수정을 합쳐 기본 3회로 관리하는 것이다. 횟수는 새 정책 제안이며 현재 전역 상한이 아니다. 한 번의 관찰에서 발견한 문제를 묶어 고치고 가장 큰 문제부터 해결한다. 기본 예산 밖의 추가 제작은 남은 문제·범위·추가 작업을 보여준 뒤 기존 위임 범위와 실행 예산에 따라 결정한다.

관찰·판정은 최소 한 번 수행하되 결함이 없으면 코드를 바꾸지 않는다. 회차는 같은 산출물의 관찰 결과를 묶어 수정하고 재검증한 한 주기로 정의한다. 새 화면·새 매체 추가로 예산을 우회하지 않도록 적용 산출물과 범위를 함께 기록한다. 개별 도구 호출·스크린샷 수는 수정 회차와 별도로 측정한다.

Critical이나 필수 Major가 남아도 예산이 끝났다는 이유로 통과시키지 않는다. 추가 수정·범위 축소·예외 수용·종료를 구분한다. 축 B 수정이 브랜드·모바일·여정에 영향을 주면 A/C와 관련 회귀도 확인한다. 모든 축을 매번 전부 실행하지도, 무조건 수정한 축 하나만 보지도 않는다.

## 9. 에이전트와 전달 정보

당장 새 팀을 크게 만들기보다 기존 제작 역할에 실제 앱·소개 장면 분기를 추가하고 축 B의 실물 검수 계약을 강화한다. 조사·전략 역할과 ID 체계는 유지한다.

- 오케스트레이터: 사용자 결정·응답 대기·범위 버전·반복 예산을 관리한다. 작업자에게 보류된 결정을 완료된 것처럼 넘기지 않는다.
- 제작자: 확정·위임된 입력만 사용하고, 필요한 새 결정을 발견하면 해당 의존 작업을 멈춰 보고한다. 결과물·변경 ID·미검증 범위·실행 증거를 반환한다.
- 소개 장면 제작자: 해당 요청에서만 Stageshow 예제·kit·촬영을 사용한다. 실제 앱 기능을 보증하지 않는다.
- 실물 검토자: 짧은 브리프·필수 기준·제품 토큰·실물·기준 예제를 받는다. 제작자 자기평가를 제외하고 필요한 증거를 직접 수집한다. 독립 실행 맥락이 없으면 재열람 자체 검수라고 표기한다.

리뷰어에게 URL/파일, 실행 방법, 필요한 인증 상태, 시작 화면, fixture 초기화 방법을 전달해 재현 가능하게 한다. 처음에는 실물에서 관찰한 내용을 기록하고 그다음 원시 실행 로그·기계 측정과 대조한다. 제작자의 '발견→수정' 서술과 원시 실행 증거를 구분해 첫 판단의 유도를 줄인다. 필수 증거에 접근할 수 없으면 해당 범위를 미검증으로 돌린다.

공통 입력 11항목을 매번 장문으로 복제하기보다 확정 브리프와 현재 결정 버전, 필요한 규칙 절, 결과물·증거 경로를 전달한다. 필수 정보 자체는 생략하지 않는다. 범위와 무관한 과거 조사·폐기안·다른 매체 규칙은 로드하지 않는다. 기록·캐시는 현재 파일·토큰·범위와 일치하는지 확인한다.

자체 예제는 반복 결함이 많은 1~2개 과업의 대조 세트부터 만든다. 목록·필터, 폼·오류, 대시보드, 설정·상세, 모바일, 소개 데모는 이후 확장 후보이며 여섯 개를 모두 선행 제작할 필요는 없다. 각 예제에 목적·상태·데이터·실제 크기·잘못된 예·수정 이유·적용하지 말아야 할 맥락을 포함한다. 기존 스택·컴포넌트를 우선하고 필수 React kit로 고정하지 않는다. 예제와 다른 브랜드·콘텐츠로 평가해 외형 수렴과 과적합을 확인한다.

## 10. 대화 행동 평가

현재 러너는 고정 답변 목록을 순서대로 넣는다. 이를 질문 ID·결정 종류·범위 버전을 확인하는 분기형 시나리오로 개선한다. 도구를 지원하는 호스트와 일반 대화 호스트를 나눠 평가한다. 대기 상태·도구 응답·실제 사용자 발화·작업 이벤트를 함께 기록하며, 에이전트가 스스로 출력한 '대기 중' 문구만으로 통과시키지 않는다.

초기에는 전체 모델 매트릭스를 돌리기보다 고위험 경계 사례부터 적은 실행으로 검증한다. 다음 21개는 대화와 매체 경계를 위한 최소 평가 과제 제안이다.

| 사례 | 기대 행동 |
|---|---|
| T01 목표·타깃이 모호함 | 결과를 바꾸는 질문을 하고 관련 전략·제작 대기 |
| T02 모든 의도·결과물이 이미 명시됨 | 이미 받은 답 재질문 없이 요청 범위 수행 |

도구 이벤트로 포착 가능한 파일 변경은 발생 시점에 기록하고 전후 해시와 대조한다. 임의 셸의 모든 파일 변경까지 포착하지 못한 환경은 관측 범위를 표시한다. snapshot·해시만으로 모든 순간적 위반을 잡았다고 주장하지 않는다.

대화 점수는 필수 의도 확인, 의존 작업의 조기 실행, 승인 재사용, 질문 이해도, 추천 근거, 범위 보존을 분리한다. 사용자에게 실제로 답하기 쉬운지는 대표 질문을 비전문 사용자에게 보여주는 이해도 확인도 필요하다. 정적 검사 통과를 사용성 검증의 대체물로 쓰지 않는다.

기존 gate_compliance의 '게이트마다 질문하고 정지' 고득점 조건은 고친다. 미확정 필수 결정에서는 대기, 이미 확정·위임된 결정에서는 재질문 없이 진행, 권한 밖 작업은 금지라는 세 조건을 함께 채점한다. 요청에서 이미 범위가 확정된 점검 시나리오에 불필요한 브리프 승인 답변을 자동 공급하지 않는다.

## 11. 실물 품질과 비용 평가

기존 절차 점수는 유지하고 실물·과업 점수를 별도로 추가한다. 대표 과제는 신규 UI, 업무 목록·필터, 폼·복구, 모바일, 기존 화면 리디자인, 소개 데모다. 텍스트 묘사만 있는 시나리오에는 실제 before UI와 데이터 fixture를 보완한다.

현행 GX와 개선 GX를 같은 모델·브리프·브랜드·데이터·환경·예산으로 비교한다. Stageshow의 효과는 소개 데모 과제에서 별도 비교한다. 먼저 한 과제로 비용·기록 적합성을 점검한 뒤 반복 표본을 늘린다.

관찰 항목은 과업 성공, 정보 위계, 제품 고유성, 밀도·가독성, 상태·모션, 범위 내 결함, 미검증 범위, 질문·재질문·대기, 시간, 캐시·미캐시 토큰이다. 평균 미감 점수로 과업 실패나 조기 실행 위반을 덮지 않는다. 버전을 가린 캡처 비교와 실제 여정 검증을 함께 사용한다.

질문 수 감소 자체를 성공으로 삼지 않는다. 필요한 의도를 빠뜨리지 않으면서 중복·불명확 질문을 줄였는지 판단한다. 범위가 다른 작업의 단순 평균 비용을 효과로 발표하지 않는다.

구현은 A의 계약 정리와 C의 평가 보강을 묶어 먼저 수행하고, B·D를 적용한 뒤 E로 확장하는 순서를 권한다. 문구만 수정한 뒤 대기 동작이 개선됐다고 선언하지 않는다. 질문을 생략하는 정책 변경은 기존 테스트의 단순 삭제로 처리하지 않고 같은 의도 보존 조건을 행동 평가로 보완한다.

새 상태 계약은 한 문서를 정본으로 두고 다른 문서는 참조한다. 두 호스트 패키지·버전·README·사이트·변경 예시를 함께 맞춘다. 외부 스킬은 버전 고정·선택 사용을 기본으로 하고 기존 라이선스·별도 자산 조건을 따른다. 실제 모델 실행은 평가 호출 수·표본·예산을 기록해 재현 가능하게 한다.

## 13. 최종 권고

전면 교체보다 **대화 상태 계약 → 작업 의도별 경로 → 최종 버전 검수 → 실물 예제·도구** 순서의 개편을 권한다. 사용자에게 중요한 결정을 충분히 묻고 답을 기다리는 강점은 보존하면서, 반복 승인·내부 모드 선택·작은 수정의 과잉 절차를 줄인다.

이전 제안의 '실물 중심 제작', '예제·검사 도구', '외부 스킬 선택 연결'은 유지한다. '실물 검증을 새로 도입해야 한다'는 식의 해석, 전역 Major 0, 현재 3회를 전체 수정 예산으로 보는 해석은 채택하지 않는다. 현재 있는 능력의 연결과 종료 조건을 정확히 고치는 것이 우선이다.
