# Stageshow와 디자인 스킬 생태계 조사 및 GX Design 개선 제안

조사일: 2026-11-04 (한국 시간). 대상: 로컬 gx-design 0.13.0. 상태: 제안이며 플러그인 동작은 변경하지 않았다.

후속 독립 검토를 반영한 권고는 [워크플로우 최종 개선 제안](2026-11-04-gx-workflow-final-improvement-proposal.md)을 따른다. 기존에도 제작 중 실물 검증은 있으며, 현행 최대 3회는 제작자 polish 루프의 상한이다. 아래의 실물 우선·Major 기준·반복 예산 제안은 후속 문서에서 최종 버전 검수·범위 내 필수 기준·새 전역 예산 제안으로 보정했다.

권고는 **기존 브리프·브랜드·진단 체계를 유지하고, UI 제작을 실행 가능한 결과물 중심으로 재배치하는 것**이다. Stageshow는 홍보용 제품 화면과 커서 데모 제작 경로에 선택적으로 연결한다. 전체 앱의 UX 개선에는 별도의 과업·데이터·상태 검증을 적용한다. 규칙 추가보다 예제, 제작 수단, 실물 비교, 완성도 통과 기준이 우선이다.

## 1. Stageshow의 실제 범위

Benji Taylor의 공식 공개 글은 2026-10-31자로 게시됐다. 제품을 소개하는 정적 UI 일러스트와 짧은 애니메이션을 React 컴포넌트로 만드는 스킬이다. 실제 앱을 작동시키는 브라우저 자동화와는 다르다. 커서 클릭은 그려지는 연출이고 장면 상태 변경은 별도로 작성한다. 따라서 커서가 메뉴를 눌렀다는 영상만으로 실제 메뉴 기능이 검증되지는 않는다. [공식 공개 글](https://benji.org/stageshow), [SKILL.md](https://github.com/benjitaylor/skills/blob/main/stageshow/SKILL.md).

확인한 저장소 main 커밋은 `802057409787133703c56001080169e347305572`이다. examples 디렉터리는 69개 항목이다. 이것을 독립적인 69개 품질 검증 사례나 69개 금본위 시나리오로 해석하지 않는다. 아래 구성과 절차는 원문과 스크립트 정적 열람에 근거하며 이번 조사에서 설치·렌더 실행은 하지 않았다. [소스 스냅샷](https://github.com/benjitaylor/skills/tree/802057409787133703c56001080169e347305572/stageshow).

| 구성 | 하는 일 | GX에서 얻을 수 있는 것 |
|---|---|---|
| SKILL.md | 배치 위치·표현·이야기·예제·화면·모션·리허설 순서 | 화면 제작 전에 보이는 크기와 주목 대상을 결정 |
| references | 구도·타이포·밀도·모션·검증 방법 | 매체에 맞는 짧은 판단 근거 |
| kit | Stage, Window, Phone, 커서·상태 전환 등 React 부품 | 매번 틀리기 쉬운 기하와 모션 구현 재사용 |
| examples / teaching | 좋은 예제와 좋고 나쁜 비교 | 추상적인 규칙을 눈으로 비교할 기준 |
| film.mjs | 장면 캡처, 프레임 시트, 관측 보고·게이트 | 실제로 본 장면에 근거한 수정 |
| jumps.mjs | 시간 샘플링과 불연속 관련 검사 | 스틸로 놓치는 튐을 보조 확인 |
| layout.mjs | 한 시점의 컨트롤·컨테이너 적합성 검사 | 텍스트·컨트롤 잘림을 보조 확인 |
| review.md | 제작자 설명을 제외한 새 맥락의 실물 검토 | 자기 평가에 끌려가지 않는 완성도 판단 |

중요한 차이는 디자인 원칙 자체보다 **좋은 출발 코드와 관측 수단까지 함께 제공**한다는 점이다. 좋은 예제의 구조를 가져와 브랜드·콘텐츠에 맞추고, 실제 폭에서 촬영해 비교한다. 제작자는 구도부터 바로잡은 뒤 모션을 만든다. 이 순서는 GX에도 적용 가치가 있다. [제작 절차](https://github.com/benjitaylor/skills/blob/main/stageshow/SKILL.md).

검사 도구의 한계도 원문에 명시돼 있다. film의 게이트 통과는 필요조건이지 충분조건이 아니며, layout은 한 시점 검사이므로 모션 승인이나 시각적 승인으로 취급하지 않는다. film·jumps는 Stageshow의 장면 계측 계약에 연결되므로 임의 앱에 파일 하나만 복사해 범용 모션 검증기로 쓸 수 있다고 가정하면 안 된다. [film 소스](https://github.com/benjitaylor/skills/blob/main/stageshow/scripts/film.mjs), [layout 소스](https://github.com/benjitaylor/skills/blob/main/stageshow/scripts/layout.mjs), [검토 계약](https://github.com/benjitaylor/skills/blob/main/stageshow/references/review.md).

실제 앱에 그대로 옮기면 안 되는 규칙은 배경 글자 막대 처리, 작은 장면의 실제 문구 수 제한, 장면을 강조하기 위한 크롭, 단일 사건에 맞춘 연출이다. 이것은 홍보 일러스트의 표현 방식이다. 업무 앱은 정보 완전성, 탐색, 오류 복구, 키보드 조작, 실제 데이터 관계를 보존해야 한다.

## 2. 많이 설치된 관련 스킬

아래는 조사 시점 skills.sh의 **개별 스킬 설치 누계 표시**다. 고유 사용자 수·활성 사용자 수·품질 순위가 아니다. 저장소 전체 별 수나 여러 명령의 설치 합계와 섞지 않았다. Stageshow는 공개 직후여서 기존 도구와 기간도 다르다.

현행 원문에서 특히 확인할 변화는 다음과 같다.

- **Taste**: 예전의 다이얼·금지 패턴 중심 설명에서 더 나아가, 후보를 생성하는 draw, 실물 측정 inspect, 실제 앱 전용 스타일·화면 패턴과 검사 분기를 제공한다. 앱에서는 표·반복 패널·작은 라벨 같은 업무 UI 구조를 허용하는 별도 판단이 있다. 업스트림의 강한 하우스 스타일이나 무작위 후보 선택을 GX의 브랜드 판단보다 우선시키지는 않는다. [README](https://github.com/Leonxlnx/taste-skill), [변경 기록](https://github.com/Leonxlnx/taste-skill/blob/main/CHANGELOG.md).
- **Impeccable**: 현재 README는 24개 명령과 62개 결정적 탐지 규칙을 설명한다. PRODUCT.md·DESIGN.md, polish/harden/adapt 등 대상별 작업, live/generate 변형 탐색을 지원한다. GX가 과거 흡수한 규칙 외에 명령 라우팅과 실제 화면에서 후보를 고르는 방식이 비교 대상이다. 전체 설치는 자체 훅과 프로젝트 맥락을 동반하므로 GX 안에서는 선택 도구로 분리하는 편이 낫다. [README](https://github.com/pbakaus/impeccable).
- **UI UX Pro Max**: 현행 SKILL.md는 79개 검색 스타일, 192개 제품 팔레트, 74개 폰트 조합, 119개 UX 가이드, 22개 기술 스택을 기재한다. 디렉터리의 요약 설명에 오래된 숫자가 남아 있어 구현 시 실제 설치본을 기준으로 삼아야 한다. [현행 SKILL.md](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/blob/main/.claude/skills/ui-ux-pro-max/SKILL.md).

## 3. 함께 볼 만한 제작·피드백 도구

이 항목들은 위 설치 누계와 같은 기준의 인기도 비교를 하지 않는다. GX의 미세 조정·실행 검증을 보완할 수 있어 선정했다.

| 도구 | 원문에서 확인한 기능 | GX 적용 판단 |
|---|---|---|
| [Emil Kowalski skills](https://github.com/emilkowalski/skills) | animate, review-animations, remove-animations, animation-performance, prototype, mobile-native, break-ui 등 | 모션을 추가하는 것뿐 아니라 제거·중단·성능·모바일·최악 데이터 검증을 분리한 것이 유용 |
| [Agentation](https://www.agentation.com/) | UI에 붙인 피드백을 선택자·컴포넌트·스타일 등의 구조화 정보로 전달, MCP로 응답·해결 | gx-redesign의 진단 ID와 연결할 선택 어댑터. 개발 환경에서 사용 |
| [DialKit](https://github.com/joshpuckett/dialkit) | 실행 중 값 조절·버전 비교·애니메이션 타이밍 편집. 여러 프레임워크 지원 | 제작자가 미세 값을 눈으로 조정하는 선택 도구. 최종값을 코드·토큰으로 고정하고 개발 패널 제거 |

Agentation은 내부 사용과 유료 제품 재배포의 조건이 다르므로 GX에 번들하기보다 사용자가 설치한 도구와 연결하는 쪽을 우선한다. Stageshow도 MIT 소스와 브랜드 아이콘·상표·별도 자산의 조건을 구분해야 한다. [Agentation 라이선스 안내](https://www.agentation.com/), [Stageshow NOTICE](https://github.com/benjitaylor/skills/blob/main/stageshow/NOTICE.md).

## 4. 현재 GX에서 이미 해결한 부분

로컬 조사에 근거한 사실이다. 외부 스킬을 새로 설치하면 처음 생기는 기능처럼 소개하지 않는다.

| 현재 자산 | 이미 있는 능력 |
|---|---|
| VISUAL-CRAFT / ANTI-TELL-CHECKLIST | Taste·Impeccable 계열의 기본 룩·요소·카피 문제를 선택적으로 도입 |
| MOTION | UI 모션·영상 모션 구분과 규칙 ID 기반 점검 |
| DESIGN-TONE-ANCHOR | 기존 브랜드·토큰 우선과 전 단계 전달 |
| DESIGN-JUDGMENT / UI-QUALITY | 과업·정보 관계·상태·예외 중심 판단 |
| DESIGN-INTELLIGENCE | UI UX Pro Max를 필요할 때만 검색, 정본 충돌 방지 |
| VISUAL-QUALITY | 대표 컷 캡처·직접 보기·최소 1회 최대 3회 수정·실제 여정 확인 |
| REVIEW-AXES | 전략 일치와 완성도 분리, 별도 맥락 검수와 동일 맥락 폴백 구별 |
| gx-redesign | 진단·목표·변경·상태·여정 ID와 before/after 추적 |
| evals | 비용 기록·블라인드 채점 원칙·격리 실행 |

특히 2026-07-29의 선택 도입 설계에 Taste·Impeccable 전체 파이프라인을 들여오지 않는 결정이 이미 있다. 이번에는 당시 결정을 무시하고 중복 설치하기보다 최신 도구에서 남은 차이를 검증해야 한다.

## 5. 완성도 개선을 막을 수 있는 지점

아래의 '영향'은 규격을 읽고 도출한 가설이다. 이번 조사에서 같은 브리프로 화면을 생성해 원인을 실험적으로 확정한 것은 아니다.

| 관찰한 규격 | 가능한 영향 | 권고 |
|---|---|---|
| gx-design은 제작·검수 뒤 실물 제작 선택 게이트를 둠. PRODUCTION-HANDOFF는 통과본이 명세라고 설명 | 화면을 보아야 알 수 있는 문제를 문서 통과 뒤에 발견할 수 있음. 프로토타입이 앞에서 나오는 경로도 있어 모든 실행이 문서만 검수하는 것은 아님 | UI 실물 요청에서는 처음부터 산출물 형식을 확정하고 대표 화면을 최종 검수 앞에 배치 |
| REVIEW-AXES는 Critical 0건을 통과 기준으로 삼고, 핵심 모드는 Major 이하를 기록만 남김 | 과업은 가능해도 밀도·시선·간격·모션이 거친 결과가 통과 가능 | 사용자가 보게 될 대표 화면·핵심 과업의 Major도 수정 대상으로 지정 |
| 좋은 예제·재사용 kit·범용 캡처 실행기가 주요 배포 자산으로 구성돼 있지 않음 | 같은 작은 구현 결정을 매번 모델이 재발명 | 소수의 실행 가능한 자체 예제와 최소 검사 도구 추가 |
| ANTI-TELL은 가짜 커서·div 가짜 대시보드를 회피 대상으로 설명 | 의도된 제품 소개 장면까지 금지로 읽힐 수 있음. 현재도 브리프 예외는 있음 | 실제 제품 UI와 명시적인 홍보 일러스트의 적용 범위를 문장으로 분리 |
| 평가표 6항목은 게이트·슬롭 회피·섹션·수치성·증거·모션 위반 | 문서가 잘 갖춰진 것과 좋은 제품 화면이 나온 것을 구별하기 어려움 | 절차 준수 점수와 화면·과업 품질 점수를 별도 보고 |

## 7. 권장 워크플로우

공통 입력에서 **작업 의도, 산출물 형식, 표면의 목적**을 구분한다. 표면은 실제 앱 UI, 홍보용 제품 장면, 그래픽·브랜드·영상으로 나눈다. 사용자의 설명과 기존 프로젝트로 결정된 것은 다시 묻지 않는다. 실행 가능한 UI를 요청한 경우 그 승인을 뒤의 실물 제작 질문에서 재요청하지 않는 규격으로 정비한다. 문서만 요청한 작업은 기존 문서 경로를 유지한다.

신규 UI 권장 순서:

1. 목표·핵심 과업·브랜드·원하는 결과물 확정.
2. 기존 화면·컴포넌트·데이터와 필요한 레퍼런스 확인.
3. 방향이 열려 있으면 소수의 대표 실물 후보 비교. 방향이 정해져 있으면 대안 만들기를 생략.
4. 대표 화면 하나와 핵심 상태를 실제로 구현하고 큰 구도·위계·밀도부터 검토.
5. 통과한 토큰과 컴포넌트로 나머지 화면 제작.
6. 정상 과업·오류 복구·최악 데이터·관련 폭·입력 방식 검증.
7. 제작자의 설명을 제외한 실물 검수와 상위 문제 수정, 회귀 확인.

리디자인은 인벤토리 → 실제 before 캡처·과업 실행 → 증거 기반 진단 → 필요한 변경만 구현 → 같은 데이터·상태·뷰포트로 after 비교 순서다. 작은 다듬기 요청에 시장 조사·전략 3안·브리프 재승인을 일괄 부과하지 않는다. 전체 리뉴얼과 브랜드 변경에는 전략 선택을 유지한다. 점검만 요청한 경우 읽기 전용을 지킨다.

Stageshow 경로는 배치 크기·핵심 장면 → 가장 가까운 예제 → 제품 토큰·콘텐츠 적용 → 스틸 구도 통과 → 모션 작성 → 폭별 촬영·프레임 확인 → 별도 실물 검수로 둔다. 실제 앱 상호작용 테스트 결과와 연출의 촬영 결과는 서로 다른 증거로 보관한다.

## 8. 예제와 실행 도구

최초 자체 예제는 6개 정도로 제한한다: 밀도 높은 목록·필터, 입력 폼·오류 복구, 데이터 대시보드, 상세·설정, 모바일 탐색, 홍보용 제품 데모. 이 수는 개발 범위를 위한 제안이다.

각 예제는 소스, 실제 크기별 캡처, 사용 목적, 콘텐츠·상태 fixture, 잘못된 버전과 수정 이유, 재사용 가능한 부분, 적용하면 안 되는 맥락을 가진다. 예제를 가져오는 이유는 시각적 정답 복제가 아니라 구조·상태·미세 구현의 품질 출발점을 높이기 위해서다. 외부 제품의 아이콘·브랜드·화면을 GX 기본 자산으로 복제하지 않는다.

UI용 도구는 기존 프로젝트의 브라우저 환경을 재사용해 캡처·폰트 로드·오버플로·콘솔·여정 결과를 모은다. MCP만 필수로 요구하지 말고 기존 Playwright 실행 환경 등 동등한 실행 수단을 허용한다. 가용하지 않으면 검증 범위를 줄여 보고한다. 검사 실패, 검사 불완전, 실제 UI 결함을 구분한다.

모션은 필요할 때만 별도 시간 샘플링을 추가하고 중단·재진입·종료·루프 연결·reduced-motion을 확인한다. Stageshow 계측은 해당 제작 경로에서 우선 쓰고, 범용 UI 검증기로 만드는 일은 별도 범위로 다룬다. 기계 검사 결과만으로 미감·과업 적합성을 승인하지 않는다.

## 9. 에이전트 설계

새 역할을 늘리는 것만으로 품질이 오르지는 않는다. 기존 오케스트레이터와 전략·조사 역할은 유지하고, 제작의 전문성과 검수의 관측 권한을 구체화한다. 아래는 개발 제안이며 이번 조사에서 실행한 에이전트 구성은 아니다.

| 역할 | 입력 | 책임·출력 | 경계 |
|---|---|---|---|
| product-ui-producer | 과업·기존 컴포넌트·브랜드·데이터·필수 상태 | 실행 가능한 UI, 주요 상태, 구현·검증 대상 목록 | 전역 브랜드·기획을 임의 변경하지 않음 |
| showcase-producer | 배치 크기·메시지·제품 토큰·참고 장면 | 제품 소개 스틸·React 데모·촬영 프레임 | 실제 앱 기능 검증을 대신하지 않음 |
| visual-reviewer | 짧은 브리프·결과 URL·캡처·기준 예제 | 프레임·위치·영향·수정 방향이 있는 상위 지적 | 제작자의 자기평가를 입력으로 받지 않고 구현 수정은 맡지 않음 |

product-ui-producer는 먼저 기존 creative-producer의 UI 분기로 구현할 수 있다. showcase-producer도 트리거가 없으면 로드하지 않는다. visual-reviewer는 기존 축 B의 실행 계약을 강화하는 역할이므로 새로운 검수 축을 만들 필요는 없다. 축 A·리디자인 축 C와 현재 ID 체계는 유지한다.

리뷰어는 브라우저·이미지 열람 권한을 가지고 필요한 증거를 직접 확인해야 한다. 결과가 나쁘다는 주장과 좋다는 주장 모두 실물 증거를 요구한다. 별도 에이전트가 없는 호스트에서는 재열람 자체 검수라고 정확히 표기한다.

## 10. 통과 기준과 평가 실험

제안하는 통과 기준은 Critical 0건에 더해 **핵심 과업·대표 화면의 Major 0건**이다. 나머지 Major는 범위·영향·보류 이유를 남긴다. 취향만 다른 선택은 Major로 올리지 않는다. 현재의 최대 3회 수정 예산을 활용해 큰 문제부터 해결하고, 예산 끝에 기준을 못 넘으면 남은 문제를 보여준다. 무한 수정 루프는 만들지 않는다.

평가 점수는 두 갈래로 유지한다. 기존 절차·근거·비용 점수는 보존하고, 별도로 과업 성공·정보 위계·제품 고유성·밀도와 가독성·컴포넌트 완성도·상태와 모션 연속성을 평가한다. 화면 유형에 따라 항목을 제외할 수 있으며, 핵심 과업 실패를 미감 평균점수로 덮지 않는다.

첫 비교는 현행 GX, 현행 GX+Stageshow(홍보 데모에만 적용), 제작·검수 개편 GX의 세 조건이다. 같은 모델·브리프·브랜드·데이터·실행 환경·예산을 쓰고, 한 번에 여러 요소를 바꾸지 않도록 첫 실험에서는 통과 기준 변경과 예제 효과도 분리해 기록한다.

6개 과제 각각 3회 실행을 초기 제안으로 둔다. 랜딩, 밀도 높은 업무 UI, 폼·오류 복구, 모바일, 기존 화면 리디자인, 제품 데모를 포함한다. 비용은 1개 과제로 먼저 점검한 뒤 전체로 확장한다. 버전을 가린 실물 비교에서 승·동률·패를 기록하고, 과업 실패·Critical/Major·미검증 범위·시간·캐시/미캐시 토큰도 함께 보고한다. 작은 표본이므로 개선율을 확정적 성능 수치로 발표하지 않는다.

## 12. 결론과 확인 범위

가장 유망한 방향은 **GX의 강점인 브리프·브랜드·증거·추적을 살리고, 제작을 예제와 실행 도구로 보강하며, 실제 화면의 Major를 고치는 것**이다. Stageshow의 적용 범위는 제품 소개 자산이며, 그 제작 방식 중 좋은 예제·실제 크기·촬영·새 맥락 검수는 전체 UI 작업에도 일반화할 수 있다.

이번 결론은 공식 문서·저장소 소스와 로컬 규격 비교에 근거한 개선 가설이다. 각 도구의 렌더·기능·성능 벤치마크와 GX A/B 실험은 아직 수행하지 않았다. 따라서 완성도 상승 폭과 비용 절감 폭은 평가 실험 뒤에 판단해야 한다.
