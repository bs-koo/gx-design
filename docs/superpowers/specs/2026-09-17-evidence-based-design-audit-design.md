# Evidence-Based Design Audit 최소 개선 설계

- 일자: 2026-09-17
- 대상: `gx-design` 0.8.0의 신규 제작 및 기존 디자인 개선 파이프라인
- 상태: 구현 계획 작성 전 승인 사양

## 목표

기존 AI-티 점검과 시각 품질 규칙을 중복 확장하지 않으면서, 화면에서 실제로 발견된 문제만 진단하고 수정하도록 `gx-redesign`의 증거 기반 진단 계약을 강화한다. `gx-design`에는 같은 기준을 예방 검수로 적용하고, 화면 산출물은 데스크톱·모바일·상호작용·키보드·대비·모션 감소 설정까지 검증한다.

## 설계 원칙

1. 새로운 20개 항목 카탈로그 파일을 만들지 않는다.
2. 이미 존재하는 규칙은 `ANTI-TELL-CHECKLIST.md`, `VISUAL-CRAFT.md`, `VISUAL-QUALITY.md`를 정본으로 유지한다.
3. 기존 문서에 없는 규칙만 가장 가까운 기존 문서에 추가한다.
4. UI·웹 화면 작업에서만 관련 참고 문서를 조건부로 읽게 한다.
5. 화면에서 관찰되지 않은 문제를 고치기 위한 전면 재설계를 금지한다.
6. 정적 이미지로 확인할 수 없는 기능은 통과로 추정하지 않고 검증 한계로 기록한다.
7. 브리프와 브랜드 기준이 의도적으로 요구하는 표현은 근거를 기록하면 허용한다.

## 현재 규칙의 재사용 범위

`ANTI-TELL-CHECKLIST.md`는 동일 카드 3개, 그라데이션 텍스트, 긴 대시, 가짜 화면, 반복 장식, 과도한 히어로 요소 등 AI 특유의 요소·카피·구조를 이미 다룬다. `VISUAL-CRAFT.md`는 색, 모서리, 그림자, 타이포그래피, 모션의 일관성을 다룬다. `VISUAL-QUALITY.md`는 실제 렌더 캡처, 시각 비평, 대비와 오버플로 같은 기계적 바닥을 다룬다. `gx-redesign/SKILL.md`는 진단, 유지 자산, before/after 매핑, 개선 목표 검수를 이미 요구한다.

따라서 구현은 기존 책임을 유지하고 빈틈만 보충한다. 같은 규칙을 여러 문서에 전문으로 복제하지 않으며, 교차 참조는 필요한 위치에 한 줄로 제한한다.

## 파일별 변경 책임

### `skills/gx-design/ANTI-TELL-CHECKLIST.md`

UI·웹 산출물에 한해 다음 누락 항목을 짧게 추가한다.

- 제품 톤과 맞지 않는 장식용 이모지
- 기능적 이유가 없는 리퀴드 글라스 효과
- 근거 없는 리뷰·별점·고객 수·성과 수치
- 내용보다 균일한 외형을 우선한 벤토 그리드
- 개발 도구가 아닌 서비스의 장식용 터미널 창
- 차이가 불명확한 3단계 요금제
- 모든 설명을 체크 표시 목록으로 만드는 구성
- 실제 제품 화면·사용 과정·결과 시연이 없는 제품 히어로
- 모든 상자와 버튼에 같은 큰 둥근 모서리를 적용하는 구성
- 결제·가입 기능이 있는데 실제 이용약관 경로가 없는 상태
- 데이터를 다루는 기능이 있는데 실제 개인정보처리방침 경로가 없는 상태

이용약관과 개인정보처리방침은 링크 존재와 경로만 검증한다. 사업자 정보, 보관 기간, 제3자 제공 등 제공되지 않은 사실을 생성하지 않고 명시적인 입력 필요 항목으로 남긴다.

기존 항목과 의미가 겹치는 흰 배경, 무지개색, 그림자, 폰트, 작은 색 띠 등은 새 문장으로 중복 추가하지 않는다. 해당 항목은 기존 `VISUAL-CRAFT.md`와 `VISUAL-QUALITY.md` 규칙을 사용한다.

### `skills/gx-redesign/SKILL.md`

단계 1 진단에 다음 계약을 추가한다.

- UI·웹 화면일 때만 `ANTI-TELL-CHECKLIST.md`를 진단 입력으로 읽는다.
- 모든 규칙을 검토하되 진단표에는 실제로 발견된 항목만 기록한다.
- 각 진단 행은 `문제/화면·위치/관찰 증거/왜 어색한지/무엇으로 바꿀지/심각도`를 포함한다.
- `해당 없음`은 진단표에서 생략한다.
- 스크린샷으로 동작을 확인할 수 없는 항목은 `검증 한계`에 기록한다.
- 카드, 흰 배경, 아이콘처럼 정상적으로도 쓰이는 패턴은 제품 목적과 콘텐츠 구조를 확인한 뒤 판정한다.

단계 3과 4에는 변경 범위 잠금을 추가한다. 제작자가 변경할 수 있는 것은 진단표에 기록된 문제와 승인된 개선 브리프 목표에 직접 연결되는 항목뿐이다. 모든 변경은 기존 before/after 표의 근거 칸에 진단 문제 또는 브리프 목표를 적는다.

단계 5에는 회귀 확인을 추가한다. 발견된 문제가 해소됐는지, 진단되지 않은 새 안티패턴이 제작 중 생기지 않았는지 확인한다.

### `skills/gx-design/SKILL.md`

신규 제작에는 수정 전 진단표를 요구하지 않는다. UI·웹 제작의 자체 점검과 최종 검수에서 `ANTI-TELL-CHECKLIST.md`를 예방 기준으로 사용한다. 브리프가 의도적으로 요구하는 패턴은 제거하지 않고 근거를 자체 검수 결과에 남긴다.

### `skills/gx-design/VISUAL-QUALITY.md`

기존 렌더 품질 루프에 UI·웹 코드 산출물의 실행 검증을 추가한다.

- 데스크톱 대표 뷰포트 1개 이상
- 모바일 대표 뷰포트 1개 이상
- 주요 버튼의 실행 결과
- 내부·외부 링크의 실제 대상과 실패 여부
- 키보드 Tab 이동 순서와 보이는 포커스 표시
- 본문 및 주요 제어 요소의 WCAG AA 대비
- 레이아웃 오버플로와 콘텐츠 가림
- 모션이 있을 때 `prefers-reduced-motion` 대체 동작

정적 이미지나 비실행 문서인 경우 버튼, 링크, 키보드, 모션은 검증 대상이 아니며 `검증 불가: 비실행 산출물`로 기록한다. 검증하지 않은 항목을 통과로 표시하지 않는다.

### `skills/gx-design/REVIEW-AXES.md`

축 B의 UI·웹 검수 입력에 실행 검증 결과를 포함한다. 실행 가능한 산출물인데 결과가 없으면 Critical로 처리한다. 비실행 산출물은 `VISUAL-QUALITY.md`의 검증 한계 기록이 있으면 결함으로 보지 않는다.

### 테스트

Python 표준 라이브러리 `unittest`로 문서 계약 테스트를 작성한다. 테스트는 자연어 전문이나 항목 순서를 고정하지 않고 다음 불변 조건만 확인한다.

- `gx-redesign` 단계 1에 발견 항목만 기록하는 진단 계약이 존재한다.
- 진단 행에 `왜 어색한지`와 `무엇으로 바꿀지`가 요구된다.
- `gx-redesign` 제작 변경이 진단 문제 또는 승인된 브리프 목표에 연결된다.
- `gx-design`과 `gx-redesign`의 UI·웹 경로가 `ANTI-TELL-CHECKLIST.md`를 조건부 참조한다.
- `VISUAL-QUALITY.md`가 데스크톱, 모바일, 버튼, 링크, 키보드 포커스, 대비, `prefers-reduced-motion`을 요구한다.
- 이용약관과 개인정보처리방침에 대해 실제 경로를 요구하고 사실의 임의 생성을 금지한다.
- 새로운 독립 카탈로그 파일을 참조하지 않는다.

현재 저장소에는 추적 중인 테스트 디렉터리가 없으므로 `tests/test_evidence_based_design_audit.py`를 만들고 `python -m unittest discover -s tests`로 실행한다.

## 데이터 흐름

### 기존 디자인 개선

1. 자산 인벤토리에서 실행 화면, 스크린샷, 디자인 파일, 코드 등 확인 가능한 증거를 수집한다.
2. 단계 1에서 기존 품질 축과 UI·웹 조건부 안티텔 점검을 수행한다.
3. 발견된 문제만 진단표에 기록하고 확인 불가능한 기능은 검증 한계로 분리한다.
4. 단계 3의 개선안은 진단 행과 승인 브리프 목표를 해결 범위로 사용한다.
5. 단계 4의 before/after 매핑이 각 변경의 출처를 추적한다.
6. 단계 5에서 문제 해소, 유지 자산 보존, 신규 회귀 여부를 확인한다.
7. 실행 가능한 UI를 실물로 제작하면 데스크톱·모바일·상호작용·접근성 검증을 완료한다.

### 신규 디자인 제작

1. 승인된 브리프와 전략을 기준으로 제작한다.
2. UI·웹일 때만 기존 안티텔 체크리스트로 예방 점검한다.
3. 의도적인 예외는 브리프 근거와 함께 기록한다.
4. 실행 가능한 UI는 렌더 품질 루프와 실행 검증을 모두 거친다.

## 실패 처리

- 진단할 화면 증거가 없으면 기억이나 설명만으로 판정하지 않고 자료를 요청한다.
- 자동 탐지 출력은 증거 후보로만 사용하고 브리프와 화면 맥락을 고려해 최종 판정한다.
- 동일한 패턴이 존재해도 실제 정보 구조나 기능에 필요하면 문제로 기록하지 않는다.
- 최대 3회의 렌더 수정 뒤에도 Critical이 남으면 자동 완료하지 않고 남은 문제와 대안을 보고한다.
- 실행 가능한 UI인데 상호작용 또는 접근성 검증을 수행할 도구가 없으면 통과를 선언하지 않고 제한 사항을 보고한다.

## 토큰 예산 보호

- 새 규칙 카탈로그를 만들지 않는다.
- 기존 문서의 관련 절에 누락 항목만 짧게 추가한다.
- `ANTI-TELL-CHECKLIST.md`와 실행 검증 규칙은 UI·웹 작업에서만 읽는다.
- 오케스트레이터 문서에는 세부 규칙을 복제하지 않고 파일 경로와 출력 계약만 둔다.
- 진단 보고에는 발견된 항목만 출력하고 해당 없음 20개 목록을 노출하지 않는다.

## 비범위

- JSON/YAML 규칙 엔진과 자동 리포트 생성기
- 소개 사이트의 시각적 리디자인
- 기존 문서 전체의 문체 또는 인코딩 정리
- 법률 문안이나 실제 사업 정보를 임의로 생성하는 기능
- 모든 디자인 작업에 UI 전용 체크리스트를 강제 로드하는 변경

## 완료 기준

1. 기존 규칙 정본을 유지하면서 누락 항목만 보완한다.
2. `gx-redesign`은 발견된 문제만 진단하고 그 문제 또는 승인 브리프 목표만 수정한다.
3. `gx-design`은 같은 규칙을 UI·웹 신규 제작의 예방 검수로 사용한다.
4. 실행 가능한 UI는 데스크톱·모바일·버튼·링크·키보드 포커스·대비·모션 감소 설정을 검증한다.
5. 비실행 산출물은 검증 한계를 명시하고 기능 통과를 주장하지 않는다.
6. 문서 계약 테스트가 `python -m unittest discover -s tests`로 통과한다.
