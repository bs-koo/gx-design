# gx-design v0.12 — 모드 재설계(비용·품질) · 결과 검증 보강 · 평가 세트

- 날짜: 2026-10-15
- 기준: feat/v0.10-motion-guide(PR #13, 0.11.0) 위에 스택 → 목표 0.12.0
- 근거: PR #13 이후 Claude·Codex 이중 채점(영역 8 + UI/UX 12), Codex 실사용 시험, 토큰 비용 추정

## 1. 문제

1. **전체 모드 비용**: 병렬 리서치 최대 4 + 완성 전략 3안(2안 폐기) + 축별 검수 + 에이전트마다 규칙 문서 전문(제작 약 2만 토큰) 재독. 에이전트 호출 ~11+ vs 핵심 ~5인데 최대 비용인 제작은 동일.
2. **핵심 모드 품질**: 품질 장치 두 개를 자른다 — (a) 전략 발산(주안 + 10줄 미니 대안 = 사실상 선택지 없음 → 콘셉트 단계 안티-슬롭 약화), (b) 검수 독립성(한 주체가 축 순차 = 자기 검수). 제작 200줄 상한은 다화면 명세를 자른다. 실사용 시험에서 랜딩 요청의 추천 모드가 핵심이었으므로 대다수 사용자가 이 모드를 쓴다.
3. **결과 검증 공백**: 개선 효과 재측정(2점대), 성능(2), 사용성 근거(1), IA(3), 접근성 증거(3), 반응형 경계(3).
4. **측정 부재**: 비용·품질 모두 추정뿐.

## 2. 설계

### 2.1 전략: 스케치 → 선택 → 확장 (양 모드 공통)

- DESIGN-IT-TWICE·gx-redesign 단계 3을 2단으로 바꾼다.
  1. **스케치 3안**: 철학이 다른 3안을 각 **10~15줄 스케치**로 만든다 — 한 줄 콘셉트 / 해결하는 문제(리디자인은 진단 ID) / 구조 요지 / 다이얼 3값+근거 / 핵심 리스크 / "not X, not Y" 부정 정의 1줄. 전략 선택 게이트는 스케치로 연다(모션 범위 문항 동반).
  2. **확장**: 선택된 1안만 design-strategy 콘셉트 형식 전체로 확장한다. 폐기안은 스케치로만 남는다.
- 발산 보장: 3안은 서로 다른 철학 축(신규 = 본질/차별화/시스템, 리디자인 = 최소 개입/리프레시/리뉴얼)을 강제하고, 같은 팔레트·같은 레이아웃 원형을 두 안이 공유하면 다시 쓴다.
- 위임: 전체 모드는 스케치 3안을 독립 작성(위임 가능 시 병렬)할 수 있고, 핵심 모드는 한 주체가 3안을 쓴다. 확장은 1회.
- 사용자가 "다른 안도 확장해서 보고 싶다"면 그 안만 추가 확장(사용자 결정).

### 2.2 리서치: frontier 기반 축 선택 (전체 모드)

- 조사 축(시장/경쟁/사용자/트렌드)은 **브리프에서 아직 열린·미검증 질문이 있는 축만** 실행한다. 사용자 자료·프로젝트 파일로 답이 난 축은 `생략: 근거`로 기록.
- 축당 외부 출처 열람 상한 8개(전체), 통합 1개 리포트는 상한 5개(핵심). 상한 도달 시 미검증으로 남긴다.

### 2.3 규칙 문서 필요 절만 읽기(점진 공개)

- VISUAL-CRAFT·VISUAL-QUALITY·MOTION·UI-QUALITY·ANTI-TELL-CHECKLIST·PROMPT-PLAYBOOK 머리에 **"읽기 지도"** 표를 둔다: `산출물 유형 | 읽을 절 | 건너뛸 절`. 예: MOTION — UI는 §0·§A·§C, 영상은 §0·§B·§C.
- 오케스트레이터의 위임 프롬프트는 문서 경로와 **읽을 절**을 함께 전달한다. 위임할 수 없으면 주 에이전트도 같은 지도로 읽는다.
- 원문 내용은 줄이지 않는다(규칙 손실 없음). 판정에 필요한 절을 건너뛰지 않도록, 검수 역할은 자기 축의 절 전체를 읽는다.

### 2.4 검수 독립성 (핵심 모드)

- 핵심 모드에서도 **축 B(완성도)는 제작과 다른 실행 맥락**에서 수행한다: 위임 가능하면 검수 역할 1개(새 맥락)에 축 B만, 축 A(전략 일치)는 오케스트레이터가 수행. 리디자인 축 C는 오케스트레이터.
- 위임할 수 없는 호스트: 주 에이전트가 축 B를 수행하되, 제작 맥락의 자기 평가를 재사용하지 않고 실물·로그를 처음부터 다시 연다(재열람 의무)고 검수 보고에 "동일 맥락 검수" 제약을 표기한다.

### 2.5 제작 분량 기준

- 핵심 모드 "분량 상한 200줄"을 **"필수 섹션 + 화면(씬)당 상한"**으로 바꾼다: 화면당 40줄, 씬당 15줄, 공통 섹션 60줄. 다화면이 잘리지 않게 한다.

### 2.6 단계별 승격 (모드 = 시작점)

- 진행 모드는 시작 깊이일 뿐이다. 아래 신호가 생기면 **해당 단계만** 전체 수준으로 올린다(사용자에게 한 줄 고지, 이미 통과한 게이트는 유지):
  - 산출물이 3종 이상이거나 화면 6개 이상
  - hard 톤 기준과 전략이 충돌
  - 사용자가 스케치 3안을 모두 거절
  - 같은 산출물 검수에서 Critical이 2회 연속
- 반대로 전체 모드라도 해당 단계의 열린 질문이 없으면 경량 실행(2.2)한다.

### 2.7 비용 기록

- 매 단계 보고 4줄에 **5번째 줄 "실행량"**을 추가: `위임 N회 · 외부 열람 N건 · 렌더 N장 · 토큰(호스트가 제공할 때만, 아니면 미측정)`.
- 최종 보고에 단계별 합계 표를 `outputs/final/YYYY-MM-DD_<project>_run-log.md`로 저장. 추정치를 측정치처럼 쓰지 않는다.
- 공통 규격은 새 문서 `skills/gx-design/RUN-BUDGET.md`(2.2·2.4·2.5·2.6·2.7의 수치와 신호를 한곳에) — SKILL 본문은 링크.

### 2.8 결과 검증 보강 (UI/UX)

- **UI-QUALITY.md**
  - §1에 **IA·과업 흐름 점검표**: 현재 위치 인지 / 다음·이전 단계 / 라벨 일관성 / 막다른 길·우회 / 핵심 과업까지 단계 수. 진단·검수가 화면 목적에 비추어 사용.
  - §3에 **상태 문구 양식**: `상태 ID | 발생 조건 | 메시지 | 다음 행동 | 입력 보존 | 복구 확인`.
  - §2에 **증거 종류별 주장 허용표**: 스크린샷 / 코드 / 실행(클릭·키보드) / 접근성 트리 / 측정 도구 / 사용자 자료 — 각각이 뒷받침할 수 있는 결론과 할 수 없는 결론.
  - §2에 **사용성 근거 구분**: 사용자 테스트·분석 자료가 제공되면 `과업 | 참여자 | 관찰 | 성공/실패` 요약, 없으면 모든 사용자 영향 서술에 `휴리스틱 추정` 표기 — 실사용자 근거처럼 쓰지 않는다.
  - §4에 **접근성 실행 체크**: 접근성 트리(이름·역할·상태), 포커스 순서·복귀, 오류-입력 연결, 확대 200%.
  - §4에 **성능 조건부 규칙**: 브리프에 성능 목표가 있거나 지연이 관찰될 때만 지표(LCP·INP·CLS 등)·기기·네트워크 조건·측정 도구를 정하고 로그. 측정 못 하면 미검증.
- **VISUAL-QUALITY.md**: 반응형 **위험 기반 폭 선택** — 기본 2폭(375×812·데스크톱) + 위험 신호별 추가(320px: 긴 한글·고정 영역 / 가로 방향: 영상·지도 / 확대 200%: 폼·표). 여정 로그 표 `경로 ID | 시작 상태 | 단계 | 기대 결과 | 실제 결과 | 실패 조건 | 증거`.
- **REDESIGN-INTERVIEW.md**: 개선 브리프 성공 기준을 **`기준 ID | 기준선(현재 관찰값) | 목표값/관찰법 | 측정 시점 | 결과`**로 기록. 인상 목표("세련되게")는 관찰 가능한 대리 기준으로 번역하거나 `정성 기준`으로 표기. 자산 인벤토리 양식 `자산 | 상태(발견/없음/접근 불가) | 시점 | 근거`.
- **creative-review/SKILL.md**·gx-redesign 단계 5: 축 C는 성공 기준 표의 **같은 관찰법으로 재측정**해 결과 열을 채운다. 변경 기록에 `변경 ID → 진단/목표 ID → 검수 결과` 추적.

### 2.9 평가 세트 (`evals/`)

- `evals/README.md` — 목적(비용·품질 측정), 실행 방법, 비용 경고, 해석 주의(표본 작음).
- `evals/scenarios/*.yaml` — 시나리오 4개: (1) 쇼핑몰 가을 랜딩(신규 UI) (2) 15초 Reels(영상 명세) (3) site/index.html 애니메이션 점검(점검 전용) (4) 대시보드 리디자인(리디자인 UI). 각 시나리오: `skill`, `request`, `mode`, `answers`(게이트별 미리 정한 답 — 질문 순서에 무관하게 쓸 수 있는 자연어 답, 예: "추천안대로 진행", "1A, 2A, 3A, 4A"), `max_turns`, `expected`(체크 항목).
- `evals/run_eval.py` — `codex exec --json`으로 시작하고 `codex exec resume <session> <answer>`로 답을 순서대로 넣는다. JSONL 이벤트에서 토큰 사용량·도구 호출 수·턴 수를 합산하고, 최종 산출물 경로를 수집해 `evals/results/<timestamp>/<scenario>-<mode>.json`에 저장. 격리 CODEX_HOME(인자) 지원, 샌드박스 지정, 시나리오·모드 필터, `--dry-run`(명령만 출력). 외부 의존 없는 표준 라이브러리 Python.
- `evals/rubric.md` — 품질 채점표: 게이트 준수(승인 전 산출물 0) / 슬롭 회피(VISUAL-CRAFT §1 기본 룩 비해당) / 필수 섹션 충족 / 수치 판정 가능 항목 비율 / 진단 행 증거 충실도 / 모션 규칙 위반 수 — 각 0~2점, 채점자(사람 또는 별도 에이전트)가 산출물만 보고 매긴다.
- `evals/score.py` — 결과 JSON들을 모아 시나리오×모드 비용 표(토큰·턴·도구 호출) 출력. 품질 점수는 rubric 채점 결과 파일을 읽어 합친다.
- `tests/`는 러너의 순수 함수(JSONL 사용량 파서, 시나리오 로더)만 단위 테스트한다 — 실제 codex 호출 없음.
